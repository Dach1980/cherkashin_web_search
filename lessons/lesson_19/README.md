# Урок 19. Упаковка MCP-сервера в EXE и переносимая установка

> Дополнительный урок. Основная программа курса заканчивается на уроке 17. Уроки 18 и 19 изучаются по желанию.

## Цель урока

До этого мы запускали MCP-сервер как Python-программу. Для этого на компьютере нужны Python, зависимости проекта и правильно настроенное окружение. Теперь разберём, как собрать приложение Windows EXE с помощью PyInstaller, что передавать на другой компьютер и как подключить собранную программу к LM Studio.

В нашем репозитории исходный код находится в src/web_search_mcp/, а функция запуска main() определена в модуле web_search_mcp.server. Сервер использует транспорт MCP stdio: сообщения идут через стандартный ввод и вывод процесса. Библиотеки перечислены в requirements.txt.

Добавим packaging/launcher.py — небольшой запускающий модуль, который вызывает существующую функцию main(). Он не заменяет сервер и не копирует его логику.

**Результат урока:** собрать каталог с EXE и необходимыми библиотеками, проверить его и подготовить переносимый комплект. Упаковка не гарантирует работу на любом компьютере без проверки: важны версия и архитектура Windows, сеть, права доступа, антивирусные ограничения и конфигурация LM Studio.

## 1. Иностранные термины

**Packaging — упаковка приложения.** Подготовка программы и необходимых файлов к распространению. Упаковка не обязательно превращает приложение в один файл.

**Executable / EXE — исполняемый файл.** Файл Windows, который операционная система может запустить как программу. Сам по себе EXE не обязательно содержит все зависимости.

**PyInstaller.** Инструмент Python, который анализирует программу, собирает интерпретатор Python и необходимые модули, затем создаёт запускаемый пакет. Это не компилятор, который превращает весь Python-код в машинный код.

**Dependency — зависимость.** Библиотека или другой компонент, необходимый программе. Нашему серверу нужны, например, пакеты MCP, HTTPX и Beautiful Soup.

**Runtime — среда выполнения.** Компоненты, необходимые для запуска приложения. PyInstaller обычно включает нужные части Python, но системные библиотеки Windows и внешние сервисы всё равно должны быть доступны.

**Entry point — точка входа.** Файл или функция, с которой начинается запуск приложения. В проекте это функция main() в src/web_search_mcp/server.py.

**Launcher — запускающий модуль.** Маленький файл, который вызывает основную функцию приложения и служит точкой входа для сборщика.

**Build — сборка.** Процесс создания распространяемого пакета из исходного проекта.

**Artifact — артефакт сборки.** Результат сборки: EXE, каталог с библиотеками, архив или другой распространяемый файл.

**One-folder / onedir.** Режим, в котором EXE и вспомогательные файлы лежат в одной папке. Его проще проверять и диагностировать, поэтому начнём с него.

**One-file / onefile.** Режим одного EXE-файла. При запуске PyInstaller обычно распаковывает внутренние компоненты во временный каталог. Такой файл удобнее передавать, но запуск может быть медленнее, а антивирусы могут проверять его строже. «Один файл» не отменяет внешние требования: конфигурация, сеть и совместимая Windows всё равно нужны.

**Bundle — комплект поставки.** Все файлы, которые нужно передать вместе: приложение, конфигурационные шаблоны и инструкция.

**Console application — консольное приложение.** Приложение с консольными каналами ввода и вывода. Они важны для нашего сервера, потому что MCP использует stdio.

**Standard input / standard output / standard error (stdin / stdout / stderr).** Стандартный ввод, стандартный вывод и стандартный поток ошибок процесса. В MCP-сервере stdout занят протокольными сообщениями. Нельзя добавлять туда произвольные print(): это может нарушить обмен сообщениями. Диагностику направляют в stderr или корректно настроенный журнал.

**Hidden import — скрытый импорт.** Модуль, который сборщик не обнаружил автоматически, например потому, что тот загружается динамически. Не нужно добавлять скрытые импорты наугад: сначала изучите сообщение об ошибке.

**Clean build — чистая сборка.** Сборка после очистки старых временных результатов. Она помогает убедиться, что результат не зависит от случайно оставшихся файлов.

**Portable application — переносимое приложение.** Программа, которую можно переместить в другую папку или на другой компьютер без классического установщика. Переносимость не отменяет внешние требования.

**Installer — установщик.** Программа, которая устанавливает приложение, создаёт ярлыки и при необходимости регистрирует настройки. В этом уроке делаем переносимый комплект, а не полноценный установщик Windows.

**Smoke test — дымовой тест.** Минимальная проверка запуска и базового сценария. Успешный запуск EXE ещё не доказывает, что LM Studio подключается к серверу и вызывает оба инструмента.

**Reproducible build — воспроизводимая сборка.** Сборка, которую можно повторить по зафиксированным исходникам и зависимостям с предсказуемым результатом. Фиксация версий повышает повторяемость.

## 2. Добавляем точку входа

Создадим файл packaging/launcher.py:

~~~python
"""Точка входа для упаковки MCP-сервера через PyInstaller."""

from web_search_mcp.server import main


if __name__ == "__main__":
    main()
~~~

Разбор кода:

1. Строка документации в тройных кавычках поясняет назначение файла.
2. from web_search_mcp.server import main импортирует готовую функцию запуска из пакета. Это не копирование кода и не создание второго сервера.
3. if __name__ == "__main__": проверяет, запущен ли файл как основная программа. При запуске EXE условие выполняется; если модуль импортирован из другого кода, блок обычно не запускается.
4. main() вызывает существующую функцию запуска MCP-сервера.

**Конструкция для акцента — if __name__ == "__main__":.** Это условие уже встречалось в Python, но здесь оно особенно важно: импорт модуля не должен самопроизвольно запускать сервер. Отделение импорта от запуска упрощает тестирование и повторное использование.

Почему не писать весь сервер внутри launcher? У проекта уже есть архитектура. Точка входа должна только передать управление существующей функции. Так меньше дублирования, проще сопровождать код и ниже риск, что EXE будет отличаться от исходного сервера.

## 3. Подготовка окружения

Откройте PowerShell в корне репозитория и проверьте папку и версию Python:

~~~powershell
Get-Location
Get-ChildItem
python --version
~~~

Если виртуальное окружение проекта называется .venv, активируйте его:

~~~powershell
.\.venv\Scripts\Activate.ps1
~~~

Если имя окружения другое, укажите фактический путь. Затем установите библиотеки проекта и PyInstaller:

~~~powershell
python -m pip install -r requirements.txt
python -m pip install pyinstaller
python -m PyInstaller --version
~~~

Почему используем python -m pip, а не просто pip? Так модуль pip запускается тем интерпретатором Python, который выбран командой python. Это снижает риск установить сборщик в другое окружение.

До упаковки запустите существующие тесты и проверьте обычный сервер по инструкции урока 12. Сборка не исправляет ошибки исходников — она упаковывает текущее приложение.

## 4. Собираем EXE в режиме onedir

Из корня репозитория выполните в PowerShell одну команду:

~~~powershell
python -m PyInstaller --noconfirm --clean --onedir --console --name web-search-mcp --paths src --collect-all mcp --collect-all httpx --collect-all bs4 packaging/launcher.py
~~~

Разбор параметров:
- python -m PyInstaller запускает сборщик через текущий Python.
- --noconfirm разрешает перезаписать результаты без интерактивного подтверждения.
- --clean очищает временный кэш сборки перед работой.
- --onedir создаёт папку с EXE и зависимостями. Для первой сборки этот режим проще в диагностике, чем onefile.
- --console сохраняет консольный режим. Не заменяйте его на --windowed: серверу нужны стандартные каналы ввода и вывода для MCP.
- --name web-search-mcp задаёт имя результата.
- --paths src добавляет каталог src в пути поиска модулей, чтобы сборщик нашёл пакет web_search_mcp.
- --collect-all mcp просит собрать данные, подмодули и ресурсы пакета MCP.
- --collect-all httpx и --collect-all bs4 аналогично собирают ресурсы HTTPX и Beautiful Soup.
- packaging/launcher.py — файл, с которого начинается сборка.

Опции --collect-all — стартовая настройка, а не универсальная гарантия. Если установленная версия библиотеки изменила структуру ресурсов, изучите предупреждения сборщика и проверьте результат. Не подавляйте предупреждения автоматически.

После успешной сборки ожидайте примерно такую структуру:

~~~text
dist/
└── web-search-mcp/
    ├── web-search-mcp.exe
    └── ... вспомогательные файлы и библиотеки ...
~~~

Содержимое зависит от версий Python, PyInstaller и библиотек. Из сборки onedir нельзя переносить только EXE: ему нужны соседние файлы. Передавайте целиком каталог dist/web-search-mcp/.

## 5. Проверяем комплект

~~~powershell
Test-Path .\dist\web-search-mcp\web-search-mcp.exe
Get-ChildItem .\dist\web-search-mcp
~~~

Первая команда должна вывести True. Вторая показывает файлы комплекта.

MCP-сервер использует stdio и ожидает, что клиент будет общаться с ним по протоколу. Поэтому запуск EXE двойным щелчком не является полной проверкой: процесс может ждать сообщения или завершиться без видимого результата. Правильная проверка — запустить сервер через LM Studio и вызвать инструменты.

Порядок:
1. Сохраните текущую конфигурацию LM Studio.
2. Временно подключите EXE как отдельный MCP-сервер с абсолютным путём.
3. Перезапустите или обновите MCP-подключение согласно используемой версии LM Studio.
4. Убедитесь, что клиент обнаружил инструменты search_web и fetch_web_page.
5. Проверьте поиск по простому запросу.
6. Проверьте загрузку конкретной публичной страницы.
7. При ошибке изучите журналы и сообщения stderr.

Не запускайте одновременно две копии одного сервера без необходимости: это усложняет диагностику и может привести к проверке не того процесса.

## 6. Конфигурация LM Studio

Расположение файла конфигурации и формат настроек могут отличаться между версиями LM Studio. Используйте интерфейс и документацию своей версии.

Ниже только иллюстрация структуры JSON, а не конфигурация, которую нужно без проверки вставлять целиком:

~~~json
{
  "mcpServers": {
    "web-search-mcp": {
      "command": "C:\\\\MCP\\\\web-search-mcp\\\\web-search-mcp.exe",
      "args": []
    }
  }
}
~~~

- mcpServers — объект со списком серверов в этом примере.
- web-search-mcp — локальное имя подключения.
- command — полный путь к EXE.
- args — список аргументов командной строки. Здесь он пуст, потому что пример не требует аргументов.

**JSON — не Python.** В JSON обратная косая черта в строке пути Windows записывается как \\\\, потому что она обозначает специальные последовательности. Если LM Studio генерирует конфигурацию через интерфейс, предпочтительнее использовать этот способ.

Если нужны переменные окружения, рабочая директория или другие параметры, учтите их отдельно в формате, поддерживаемом вашей версией LM Studio. Не добавляйте неизвестные поля наугад.

## 7. Почему stdio влияет на упаковку

Сервер передаёт протокольные сообщения через стандартный ввод и вывод процесса. Поэтому:
- оставляем --console, а не --windowed;
- не добавляем диагностические print(), которые пишут в stdout;
- сохраняем существующее логирование в stderr;
- не превращаем сервер в фоновое GUI-приложение без консольных каналов;
- проверяем EXE именно из LM Studio.

Если в stdout появляется обычный текст вроде «Сервер запущен!», MCP-клиент может принять его за повреждение потока протокола. Отладка должна идти через правильный поток журналирования.

## 8. Переносимая установка

После проверки скопируйте весь каталог dist/web-search-mcp/ в постоянное место, например:

~~~text
C:\MCP\web-search-mcp\
    web-search-mcp.exe
    ... остальные файлы сборки ...
~~~

Не меняйте файлы внутри каталога вручную и не переносите только EXE. Обновите путь в настройке LM Studio на постоянное местоположение и повторите проверку обоих инструментов.

Для распространения можно создать ZIP-архив:

~~~powershell
Compress-Archive -Path .\dist\web-search-mcp\* -DestinationPath .\dist\web-search-mcp-windows.zip -Force
~~~

Compress-Archive — встроенная команда PowerShell для создания ZIP-архива. Параметр -Path задаёт содержимое, -DestinationPath — имя архива, -Force разрешает заменить существующий архив. При распаковке должна сохраниться структура каталога.

На другом компьютере распакуйте архив в постоянную папку, укажите EXE в конфигурации LM Studio и проведите полный тест. EXE для Windows не является приложением для macOS или Linux. Нужно учитывать архитектуру и версию Windows.

## 9. Режим onefile

Для сравнения сборка одним файлом выглядит так:

~~~powershell
python -m PyInstaller --noconfirm --clean --onefile --console --name web-search-mcp --paths src --collect-all mcp --collect-all httpx --collect-all bs4 packaging/launcher.py
~~~

В режиме --onefile результат обычно находится в dist/web-search-mcp.exe. Он удобнее для передачи, но не обязательно лучше для MCP-сервера:
- запуск может быть медленнее из-за распаковки;
- запуск может блокироваться политиками безопасности;
- диагностика внутренних файлов менее очевидна;
- некоторые антивирусы строже проверяют самораспаковывающиеся EXE;
- внешняя конфигурация и доступ к интернету никуда не исчезают.

Рекомендуемый маршрут: сначала --onedir, полный тест и проверка на отдельной тестовой машине, а затем при необходимости эксперимент с --onefile.

## 10. Переменные окружения и секреты

Не записывайте пароли, API-ключи и приватные данные прямо в launcher или команду сборки. Передача EXE сама по себе не переносит значения переменных окружения на другой компьютер. Их нужно безопасно настроить отдельно.

Проверьте, какие параметры реально читаются из src/web_search_mcp/config.py. Не создавайте второй механизм конфигурации, если существующего достаточно. Не включайте секреты и локальные файлы окружения в репозиторий или публичный архив.

## 11. Типичные ошибки

**EXE не появился.** Проверьте результат команды PyInstaller, текущий каталог и наличие packaging/launcher.py.

**Не найден web_search_mcp.** Убедитесь, что сборка выполняется с --paths src и пакет действительно находится в src/web_search_mcp/.

**Ошибка импорта после сборки.** Изучите сообщение PyInstaller о пропущенных модулях. При необходимости добавьте точечный --hidden-import имя_модуля или настройку ресурсов. Не добавляйте сотни модулей вслепую.

**LM Studio не видит инструменты.** Проверьте путь к EXE, запуск процесса, конфигурацию клиента и stderr. Убедитесь, что сохранён консольный режим и нет отладочного текста в stdout.

**Поиск работает, а загрузка страницы нет.** Упаковка не устраняет сетевые ограничения. Проверьте интернет, DNS, TLS-сертификаты, правила сайта и ограничения, реализованные в web_fetch.py.

**На другом компьютере не запускается.** Проверьте архитектуру, версию Windows, права пользователя, антивирусную блокировку, наличие всех файлов onedir и системные требования. Не ограничивайтесь проверкой на компьютере разработчика.

**Собран устаревший код.** Выполните чистую сборку с --clean и проверьте, что используете актуальные файлы. После изменения исходников повторите тесты, пересоберите EXE и снова проверьте оба инструмента.

**Антивирус предупреждает о файле.** Не отключайте защиту бездумно и не просите пользователя игнорировать предупреждение. Проверьте источник сборки и версии инструментов. Подпись кода и распространение через доверенный канал — отдельные темы.

## Итог урока

PyInstaller позволяет подготовить Windows-пакет, для запуска которого обычно не требуется отдельно устанавливать Python-окружение проекта. Но он не заменяет тестирование, конфигурацию LM Studio, проверку сети и аккуратное обращение с секретами. Для нашего MCP-сервера безопаснее начать с onedir, передавать комплект целиком и проверять его через реальный MCP-клиент.
