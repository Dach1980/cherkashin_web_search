## 1. Зачем нам этот проект

Представим, что на компьютере установлена локальная языковая модель, например Qwen, которая запускается через LM Studio.

Языковая модель умеет отвечать на вопросы, объяснять сложные темы, анализировать текст и писать код. Но её собственные знания не гарантируют, что она знает самые свежие события или актуальное состояние документации. Сама по себе модель также не получает автоматического доступа ко всем сайтам в интернете.

Если спросить её о свежем выпуске программы, изменившейся инструкции или новой версии библиотеки, модель может ошибиться или ответить на основе устаревших сведений. Иногда ответ звучит уверенно, хотя актуальных данных у модели нет.

Один из способов улучшить ответы — предоставить модели внешние инструменты. Мы создадим собственную Python-программу, которая предоставит две возможности:

1. **Web Search** — найти в интернете страницы, подходящие под запрос, и вернуть список результатов.
2. **Web Fetch** — открыть выбранную веб-страницу, извлечь из неё текст и вернуть его модели для анализа.

Например, пользователь спрашивает:

> Найди актуальную документацию по библиотеке Python и объясни, как установить её в Windows.

Возможный сценарий работы:

1. Модель понимает, что для точного ответа нужны актуальные сведения.
2. Через MCP она вызывает инструмент `web_search`.
3. Python-сервер выполняет поисковый запрос и возвращает названия страниц, ссылки и краткие описания.
4. Модель выбирает подходящую страницу и вызывает `web_fetch`, передав ей URL.
5. Сервер загружает страницу и извлекает из неё читаемый текст.
6. Модель анализирует текст и формирует ответ пользователю.

**Главная идея:** мы не создаём новую языковую модель. Мы пишем программу, которая предоставляет уже существующей модели полезные внешние возможности.

## 2. Основные понятия

В проекте встречаются английские термины. Это обычная практика в программировании: названия библиотек, функций, протоколов и технических понятий часто используют английские слова. Важно не просто запоминать их, а понимать смысл.

### 2.1. Python

**Python (Пайтон)** — язык программирования общего назначения. На нём можно писать скрипты, веб-сервисы, автоматизацию, анализ данных и приложения с искусственным интеллектом.

**Язык программирования** — формальный способ описать компьютеру действия, которые он должен выполнить.

Python выбран для учебного проекта по нескольким причинам:

- у него сравнительно понятный синтаксис, удобный для начинающих;
- для работы с HTTP-запросами, HTML, JSON и MCP доступны готовые библиотеки;
- на Python удобно отдельно разрабатывать функции, тестировать их и объединять в приложение;
- программу можно запускать на Windows, а при необходимости переносить на другие операционные системы с учётом их особенностей.

**Синтаксис** — правила записи команд и выражений языка. Как в естественном языке есть правила построения предложений, так и в Python есть правила, по которым записывается код.

**Библиотека** — готовый набор программных компонентов, которые можно использовать в своём коде, чтобы не реализовывать всё самостоятельно. Например, библиотека для HTTP-запросов берёт на себя значительную часть работы по обмену данными с веб-сайтами.

### 2.2. Локальная языковая модель

**Языковая модель (Language Model, LM)** — программа машинного обучения, которая обрабатывает и генерирует текст, а также может выполнять другие задачи в зависимости от её возможностей и обучения.

**Локальная модель** — модель, которую запускают на собственном компьютере или на управляемом пользователем локальном сервере, а не обязательно отправляют запросы к удалённому облачному сервису.

Примеры моделей — Qwen и другие семейства больших языковых моделей.

**Большая языковая модель (Large Language Model, LLM)** — языковая модель, обученная на больших объёмах данных и способная решать широкий круг задач с текстом.

Локальный запуск может дать больше контроля над окружением и данными. Однако само слово «локальная» не означает, что вся программа полностью автономна: если мы подключаем Web Search и Web Fetch, эти компоненты обращаются к внешним веб-сайтам. Нужно различать локальную модель и сетевые инструменты, которыми она пользуется.

### 2.3. LM Studio

**LM Studio** — настольное приложение для загрузки и запуска совместимых языковых моделей на компьютере. В нашем проекте оно будет выступать приложением, в котором пользователь общается с моделью и настраивает доступ к MCP-серверам.

LM Studio — не сама модель и не наш Python-сервер. Это приложение, которое помогает запускать модель и взаимодействовать с ней.

Упрощённо:

- **Qwen** — модель, которая интерпретирует запрос и формирует ответ;
- **LM Studio** — приложение, в котором модель запускается и с которым взаимодействует пользователь;
- **наш Python-сервер** — отдельная программа, предоставляющая модели инструменты поиска и загрузки страниц.

Поддерживаемые способы подключения и элементы интерфейса LM Studio могут меняться между версиями. Когда дойдём до подключения, будем сверяться с фактической установленной версией приложения.

### 2.4. Web Search — веб-поиск

**Web Search** буквально означает «поиск в интернете». В нашем проекте это функция, которая принимает текстовый запрос и возвращает список найденных страниц.

Например, на входе:

`как установить библиотеку httpx в Python`

Условный результат:

- название страницы;
- URL страницы;
- краткий фрагмент текста или описание;
- при наличии — дополнительная информация, предоставленная поисковым источником.

**Запрос (query)** — данные, которые передаются поисковой системе для поиска. В данном случае это строка с вопросом или набором ключевых слов.

**Результат поиска (search result)** — отдельная найденная запись, обычно содержащая название, ссылку и описание.

**URL (Uniform Resource Locator)** — адрес ресурса в интернете, например адрес веб-страницы. Именно URL позволяет указать, какую страницу нужно открыть.

Поиск не равен чтению страницы. Поисковая система может вернуть краткое описание и ссылку, но для подробного анализа часто нужно получить содержимое самой страницы.

### 2.5. Web Fetch — получение содержимого страницы

**Fetch** в данном контексте означает «получить» или «загрузить». Инструмент Web Fetch получает содержимое страницы по URL и старается извлечь из него текст, полезный для модели.

Упрощённый пример:

- Web Search нашёл официальную документацию;
- Web Fetch открыл страницу документации;
- сервер убрал лишнюю разметку и вернул читаемый текст;
- модель прочитала этот текст и использовала его при подготовке ответа.

Веб-страницы обычно содержат не только основной текст, но и HTML-разметку, меню, рекламные блоки, ссылки, элементы навигации и скрипты.

**HTML (HyperText Markup Language)** — язык разметки, с помощью которого задаётся структура веб-страницы. HTML — не то же самое, что обычный текст статьи.

**Извлечение текста** — обработка загруженного содержимого с целью получить основную текстовую информацию, пригодную для чтения и анализа.

Важно понимать ограничение: не каждую страницу можно качественно извлечь обычным HTTP-запросом. Некоторые сайты строят содержимое с помощью JavaScript, требуют авторизации, блокируют автоматические запросы или показывают текст только после дополнительных действий. В учебном проекте мы предусмотрим понятные ошибки для таких ситуаций, а не будем обещать, что любая страница обязательно загрузится.

### 2.6. MCP — Model Context Protocol

**MCP (Model Context Protocol)** — протокол взаимодействия, который позволяет AI-приложениям обнаруживать и вызывать внешние инструменты и получать от них результаты в согласованном формате.

По-русски его можно описать как стандартизированный способ подключать к AI-приложению внешние возможности: инструменты, источники данных и другие поддерживаемые ресурсы.

**Протокол** — набор согласованных правил обмена сообщениями между программами. Если обе стороны соблюдают протокол, они могут взаимодействовать без необходимости придумывать уникальный формат общения для каждой пары приложений.

В нашем проекте MCP нужен для того, чтобы LM Studio могла узнать о доступных инструментах и вызвать их по установленным правилам.

MCP не является поисковой системой, не генерирует ответы вместо модели и сам по себе не гарантирует правильность результатов. Он задаёт способ взаимодействия между приложением и сервером инструментов.

### 2.7. MCP-сервер

**Сервер** — программа, которая предоставляет определённые возможности другой программе, принимая запросы и возвращая результаты. В данном контексте слово «сервер» не обязательно означает отдельный компьютер в интернете: процесс может запускаться на том же компьютере, что и LM Studio.

**MCP-сервер** — программа, которая реализует MCP и объявляет доступные через него инструменты.

Наш MCP-сервер будет написан на Python и предоставит как минимум два инструмента:

- `web_search`;
- `web_fetch`.

Сервер не должен сам угадывать, когда модель хочет выполнить поиск. Он сообщает приложению, какие инструменты доступны, и выполняет вызов, когда приложение и модель инициируют его предусмотренным способом.

### 2.8. Инструмент (tool)

**Tool** — английское слово «инструмент». В контексте AI-приложений это вызываемая функция или операция, которая выполняет определённую задачу за пределами обычной генерации текста.

Примеры наших инструментов:

- `web_search` — найти страницы по запросу;
- `web_fetch` — получить текст по URL.

Название инструмента, его описание и схема входных данных помогают приложению и модели понять, для чего он предназначен и какие параметры нужно передать.

**Параметр** — входное значение, которое функция получает для выполнения работы. Например, для `web_search` параметром будет поисковый запрос.

**Возвращаемое значение** — результат, который функция передаёт обратно вызвавшему её коду. Для поиска это может быть список результатов, а для загрузки страницы — извлечённый текст и информация о странице.

В следующих уроках мы разберём эти понятия на обычных функциях Python, а затем зарегистрируем функции как MCP-инструменты.

## 3. Как будут взаимодействовать компоненты

Ниже — упрощённая схема будущей системы:

```text
Пользователь
    |
    v
LM Studio + языковая модель Qwen
    |
    | модель решает, что нужны внешние сведения
    v
MCP-клиент в приложении
    |
    | вызов инструмента по MCP
    v
Наш Python MCP-сервер
    |
    +---- web_search ----> поисковый источник в интернете
    |                           |
    |<----- список страниц -----+
    |
    +---- web_fetch ------> выбранный веб-сайт
    |                           |
    |<----- текст страницы -----+
    |
    v
Результат возвращается в LM Studio
    |
    v
Модель анализирует данные и отвечает пользователю
```

**MCP-клиент** — сторона приложения, которая устанавливает взаимодействие с MCP-сервером и отправляет ему предусмотренные протоколом запросы. В нашем сценарии роль клиентской стороны выполняет поддерживающее MCP приложение, а не отдельная функция поиска.

Схема показывает логические роли. Реальная последовательность сообщений зависит от версии приложения, модели и используемого транспорта MCP, но принцип остаётся таким: приложение подключается к серверу, узнаёт его инструменты, инициирует вызовы и передаёт результаты модели.

### Пример работы по шагам

Допустим, пользователь пишет: «Найди официальную инструкцию по установке пакета и объясни её».

**Шаг 1. Модель анализирует задачу.** Она решает, что актуальную инструкцию лучше получить из внешнего источника.

**Шаг 2. Модель запрашивает поиск.** Через приложение вызывается `web_search` с текстом запроса.

**Шаг 3. Сервер выполняет поиск.** Он обращается к выбранному поисковому источнику и приводит ответ к ожидаемому формату.

**Шаг 4. Результаты возвращаются модели.** Модель получает список страниц и может выбрать наиболее подходящую, например официальную документацию.

**Шаг 5. Вызывается загрузка страницы.** Модель передаёт URL в `web_fetch`.

**Шаг 6. Сервер получает и обрабатывает содержимое.** Он загружает страницу с ограничением времени и размера ответа, извлекает текст и возвращает его.

**Шаг 7. Модель формирует ответ.** Она использует полученные данные, чтобы объяснить инструкцию. Если источники не дают нужного ответа, модель не должна притворяться, будто поиск прошёл успешно.

Это пример возможного сценария, а не обещание, что модель всегда выберет правильный источник или сделает ровно два вызова. Поведение зависит от запроса, описаний инструментов, модели и результатов поиска.

## 4. Почему Web Search и Web Fetch — два отдельных инструмента

На первый взгляд можно попытаться сделать одну функцию, которая сразу ищет, открывает страницы и возвращает большой текст. Но разделение на два инструмента делает систему понятнее.

| Критерий | Web Search | Web Fetch |
|---|---|---|
| Главная задача | Найти подходящие страницы | Получить содержимое конкретной страницы |
| Основной вход | Поисковый запрос | URL |
| Основной результат | Список результатов поиска | Текст страницы и метаданные |
| Типичная ошибка | Поиск ничего не нашёл или источник недоступен | Страница не открывается или текст не извлекается |
| Кто определяет следующий шаг | Модель выбирает результат | Модель анализирует загруженный материал |

**Метаданные** — дополнительные сведения об объекте. Для страницы это могут быть заголовок, URL, код ответа сервера и другие характеристики.

Разделение даёт несколько преимуществ:

1. **Проще проверять.** Можно проверить поиск независимо от загрузки страниц.
2. **Проще исправлять.** Если результаты находятся, но страницы не загружаются, причина вероятнее всего в Web Fetch, а не в поиске.
3. **Меньше лишней работы.** Не нужно скачивать каждую найденную страницу, если достаточно краткого описания.
4. **Больше контроля у модели.** Модель может выбрать, какую именно страницу читать.
5. **Удобнее тестировать.** Для каждой функции можно написать отдельные тесты.

## 5. Почему сначала пишем обычные функции, а потом MCP-сервер

Мы будем разрабатывать проект постепенно, слоями.

Сначала создадим обычную функцию Python для поиска и проверим, что она принимает запрос и возвращает данные в ожидаемом формате. Затем отдельно сделаем загрузку и извлечение текста страницы. И только после этого подключим функции к MCP.

**Функция** — именованный блок кода, который выполняет определённую задачу и может быть вызван из другого места программы.

Такой порядок важен по нескольким причинам:

- если поиск работает неправильно, мы сможем проверять его без участия MCP;
- если MCP не подключается, не придётся сразу подозревать и поиск, и обработку HTML, и сетевой код;
- функции проще тестировать отдельно;
- каждая часть проекта будет иметь ясную ответственность.

**Тестирование** — проверка программы на заранее заданных примерах, чтобы выяснить, соответствует ли её поведение ожиданиям.

**Отладка (debugging)** — процесс поиска и устранения причины неправильного поведения программы.

Мы не будем сразу писать большой файл на сотни строк. Каждый новый компонент сначала получит небольшую, понятную задачу, затем мы проверим его работу и только потом перейдём к следующему слою.

## 6. Из чего будет состоять проект

По мере прохождения курса в репозитории появятся следующие части. Точный состав файлов может уточняться, когда мы проверим совместимость библиотек и реализацию MCP SDK.

- **Настройки.** Имя сервера, тайм-ауты и допустимые размеры результатов.
- **Web Search.** Поиск и преобразование результата в единый формат.
- **Web Fetch.** Загрузка страницы и извлечение текста.
- **MCP-сервер.** Регистрация инструментов и обработка вызовов по протоколу.
- **Тесты.** Автоматические проверки ожидаемого поведения.
- **Инструкция запуска.** Подключение к LM Studio и проверка работы.

**Репозиторий (repository)** — хранилище файлов проекта вместе с историей изменений. В нашем случае он находится на GitHub.

**Зависимость (dependency)** — внешняя библиотека или пакет, от которого зависит работа программы.

**Пакет (package)** — распространяемый набор Python-модулей. В ходе курса мы установим нужные пакеты и зафиксируем список зависимостей проекта.

**Конфигурация (configuration)** — настройки, которые определяют поведение программы без необходимости переписывать её основную логику.

## 7. Как будет запускаться сервер

Итоговая цель — настроить LM Studio так, чтобы она могла запускать наш MCP-сервер и обращаться к его инструментам без необходимости каждый раз открывать VS Code и вручную запускать команду в терминале.

**VS Code (Visual Studio Code)** — редактор кода, в котором удобно создавать и изменять файлы проекта. Это рабочий инструмент разработчика, а не обязательная часть работы готового сервера.

**Терминал** — текстовый интерфейс, в котором можно выполнять команды операционной системы и запускать программы.

Во время разработки мы будем использовать VS Code и терминал: запускать примеры, смотреть ошибки и выполнять тесты. В финале настроим запуск через LM Studio. Когда настройка будет выполнена корректно, закрытый редактор не должен сам по себе мешать запуску сервера.

При этом Python и необходимые зависимости должны оставаться установленными в окружении, из которого LM Studio запускает сервер. Закрытие VS Code не означает, что программу можно запускать без Python.

Дополнительная цель — при необходимости собрать приложение в исполняемый файл, например `.exe`. Это отдельная задача: упаковка может потребовать настройки путей, зависимостей и проверки совместимости. Мы не будем усложнять первые уроки этой темой.

## 8. Почему нельзя забывать о безопасности

Наш сервер будет получать URL от внешнего вызывающего кода и обращаться по этим адресам в сеть. Поэтому недостаточно просто написать запрос к любому адресу, который передала модель.

**Валидация (validation)** — проверка входных данных на соответствие ожидаемым правилам.

**Тайм-аут (timeout)** — ограничение времени ожидания операции. Он помогает не ждать бесконечно, если сайт не отвечает.

**Лимит размера ответа** — максимальный объём данных, который сервер готов принять или вернуть. Он помогает избежать чрезмерного расхода памяти и передачи огромных страниц модели.

**Перенаправление (redirect)** — ответ сервера, предлагающий перейти с одного URL на другой. При загрузке страницы важно проверять не только исходный адрес, но и адреса, на которые ведут перенаправления.

В проекте необходимо предусмотреть следующие меры:

- проверять формат URL и разрешённые схемы, например использовать только HTTP и HTTPS;
- не разрешать обращения к локальным и частным сетевым адресам, которые могут вести к внутренним службам компьютера или сети;
- контролировать перенаправления, чтобы проверка исходного URL не обходилась переходом на запрещённый адрес;
- ограничивать время ожидания и объём загружаемого содержимого;
- корректно обрабатывать ошибки сети, HTTP-ответы с ошибками и неподдерживаемые типы содержимого;
- не выводить отладочные сообщения в стандартный поток вывода, если он используется MCP для обмена сообщениями.

**SSRF (Server-Side Request Forgery)** — класс уязвимостей, при котором программу заставляют отправлять запросы к адресам, которые не должны быть доступны вызывающему. Для веб-загрузчика это особенно важно: опасный URL может указывать не на обычную страницу, а на внутренний ресурс.

Одна только проверка текста URL не всегда достаточна. При реализации нужно учитывать перенаправления и то, как сетевой клиент разрешает имена хостов в IP-адреса. Эти меры мы подробно рассмотрим в уроке по безопасности.

## 9. Как будем проверять качество работы

Мы будем проверять не только то, что программа «запустилась», но и то, что она правильно реагирует на разные ситуации.

Примеры проверок:

- поиск возвращает список результатов ожидаемого формата;
- пустой поисковый ответ не вызывает аварийного завершения;
- неправильный URL отклоняется;
- недоступный сайт приводит к понятной ошибке;
- слишком большой ответ не обрабатывается без ограничений;
- MCP-сервер объявляет оба инструмента;
- каждый инструмент принимает правильные параметры;
- сервер возвращает результат в формате, который может обработать клиент;
- модель может использовать найденную информацию в ответе.

**Регрессионный тест** — тест, который повторно проверяет уже исправленное поведение. Он нужен, чтобы последующие изменения случайно не сломали ранее работающую функцию.

В тестах сетевые ответы часто лучше имитировать заранее подготовленными данными, а не полагаться исключительно на живой интернет. Такой подход делает проверку повторяемой: результат теста меньше зависит от временной недоступности сайта или изменения поискового сервиса.

## 10. Ограничения, о которых нужно помнить

Даже после подключения Web Search и Web Fetch нельзя считать, что модель автоматически становится безошибочной.

1. Поисковый источник может вернуть нерелевантные или устаревшие результаты.
2. Страница может быть недоступна, измениться или блокировать автоматическую загрузку.
3. Извлечённый текст может потерять часть структуры исходной страницы.
4. Модель может неправильно интерпретировать полученные данные.
5. Внешний сайт может содержать недостоверный материал или текст, пытающийся повлиять на поведение модели.
6. Доступность поиска без обязательного API-ключа зависит от выбранного источника, его правил и текущего состояния. Мы выберем вариант и проверим его в соответствующем уроке, но не будем считать его неизменным навсегда.

**API (Application Programming Interface)** — программный интерфейс, то есть согласованный способ, с помощью которого одна программа обращается к возможностям другой.

**API-ключ** — секретный или идентифицирующий токен, который некоторые сервисы требуют для доступа к API. Его нельзя бездумно публиковать в репозитории или вставлять в открытый код.

В этом курсе мы будем стремиться использовать поисковый источник, который не требует обязательного API-ключа для выбранного сценария. Но это не означает, что любой поисковый сервис всегда доступен бесплатно или без ограничений.
