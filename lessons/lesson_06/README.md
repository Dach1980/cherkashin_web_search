## 1. Почему нельзя бесконечно хранить весь код в одном файле

Представим, что мы пишем программу для веб-поиска. Сначала в ней есть только запрос и список результатов. Позже появляются новые задачи:
- загрузить страницу из интернета;
- проверить URL;
- обработать тайм-аут;
- извлечь заголовок и текст из HTML;
- ограничить длину результата;
- зарегистрировать инструмент MCP;
- передать результат в LM Studio.

Если всё разместить в одном огромном файле, его будет трудно читать, проверять и изменять. Исправление одной части может случайно повлиять на другую.

Программный проект обычно делят на логические части. Например:

~~~text
cherkashin_web_search/
├── .venv/                  виртуальное окружение
├── src/
│   └── web_search_mcp/
│       ├── __init__.py
│       ├── config.py       настройки
│       ├── search.py       будущая логика веб-поиска
│       └── fetch.py        будущая загрузка страницы
├── tests/                  автоматические проверки
├── lessons/                материалы курса
├── requirements.txt        список зависимостей
└── .gitignore              исключения для Git
~~~

Это пример структуры, а не требование создавать все файлы прямо сейчас. В репозитории курса часть этих элементов уже подготовлена; мы разберём, для чего они нужны.

**Архитектура** (*architecture*) — способ организации частей программы и взаимодействия между ними. Хорошая архитектура помогает понимать, где искать настройки, где находится логика поиска и где должны располагаться тесты.

## 2. Модуль: отдельный файл Python

**Модуль** (*module*) — файл Python, который можно подключить к другой программе и использовать его функции, классы и переменные. Обычно модуль имеет расширение `.py).

Например, файл `config.py` может содержать настройки сервера:

~~~python
SERVER_NAME = "web-search-mcp"
DEFAULT_TIMEOUT_SECONDS = 15
DEFAULT_MAX_SEARCH_RESULTS = 5
DEFAULT_MAX_PAGE_CHARS = 12_000
~~~

Здесь каждая строка создаёт имя и связывает его со значением. Мы уже изучили оператор присваивания `=) в уроке № 3. Заглавные буквы в именах констант — общепринятая договорённость Python: так программисту показывают, что значение задумано как настройка, которую обычно не меняют в процессе работы.

Важно: заглавные буквы не делают значение технически неизменяемым. Python позволяет присвоить такому имени другое значение. Это соглашение для читабельности кода.

### 2.1. Создаём собственный модуль

Создайте в папке проекта файл `config.py` со следующим содержимым:

~~~python
SERVER_NAME = "web-search-mcp"
DEFAULT_TIMEOUT_SECONDS = 15
DEFAULT_MAX_SEARCH_RESULTS = 5

def describe_server():
    return f"Сервер {SERVER_NAME}, тайм-аут {DEFAULT_TIMEOUT_SECONDS} сек."
~~~

В этом файле есть:
- три переменные с настройками;
- функция `describe_server()`, которая возвращает текст с помощью `return`;
- f-строка, в которую подставляются значения переменных.

Обратите внимание: функция использует имена, определённые на уровне модуля. Это позволяет держать связанные настройки рядом с функцией, которой они нужны. Пока мы не углубляемся в область видимости: её основы мы уже разбирали в уроке № 4.

### 2.2. Импортируем модуль

Теперь создайте рядом файл `main.py):

~~~python
import config

print(config.SERVER_NAME)
print(config.DEFAULT_MAX_SEARCH_RESULTS)
print(config.describe_server())
~~~

Запустите из этой папки:

~~~powershell
python main.py
~~~

Ожидаемый результат:

~~~text
web-search-mcp
5
Сервер web-search-mcp, тайм-аут 15 сек.
~~~

Разберём новую конструкцию `import config`.

- `import` — ключевое слово, которое подключает модуль.
- `config` — имя файла без расширения `.py).
- точка в `config.SERVER_NAME) отделяет имя модуля от имени, которое в нём находится.
- `config.describe_server()) вызывает функцию, определённую в модуле `config).

**Преимущество:** в `main.py) остаётся логика запуска программы, а настройки и функция их описания хранятся отдельно. Когда настройки разрастутся, их можно будет изменять, не превращая главный файл в длинный перечень констант.

### 2.3. Импорт конкретных имён

Вместо импорта всего модуля можно импортировать конкретные значения:

~~~python
from config import SERVER_NAME, describe_server

print(SERVER_NAME)
print(describe_server())
~~~

Новая конструкция — `from ... import ...).

- `from config) указывает модуль-источник;
- `import SERVER_NAME, describe_server) перечисляет имена, которые нужно сделать доступными в текущем файле;
- после такого импорта можно обращаться к ним без префикса `config.).

Какой вариант лучше? Для учебного проекта чаще удобно писать `import config), потому что выражение `config.SERVER_NAME) явно показывает, откуда взялась настройка. Импорт отдельных имён тоже полезен, если требуется лишь небольшая часть большого модуля.

Не стоит импортировать всё подряд через `from config import *). Звёздочка означает импорт имён, доступных для такого импорта, но в большом проекте становится сложнее понять, откуда пришла конкретная переменная или функция. Явный импорт легче читать и отлаживать.

## 3. Пакет и библиотека: в чём разница

Эти термины часто встречаются вместе, но обозначают не совсем одно и то же.

### 3.1. Пакет Python

**Пакет** (*package*) — способ объединить несколько модулей в общую структуру с именем. Часто это папка с файлами Python. В традиционном варианте внутри такой папки находится файл `__init__.py), который помогает Python распознавать пакет и может содержать код его инициализации.

Пример:

~~~text
web_search_mcp/
├── __init__.py
├── config.py
├── search.py
└── fetch.py
~~~

Здесь `config.py), `search.py) и `fetch.py) — отдельные модули. Вместе в папке `web_search_mcp) они образуют пакет проекта.

**Инициализация** (*initialization*) — подготовка объекта или компонента к работе. Файл `__init__.py) может быть пустым; его не обязательно заполнять кодом.

В современных версиях Python существуют и так называемые пространства имён пакетов, которым `__init__.py) не всегда требуется. Но для нашего учебного проекта явный файл `__init__.py) — понятный и распространённый вариант.

### 3.2. Библиотека

**Библиотека** (*library*) — готовый код, который программист использует для решения определённых задач, вместо того чтобы писать всё с нуля. Библиотека может включать один модуль или множество пакетов.

Примеры библиотек и пакетов, которые важны для курса:
- `httpx) — библиотека для HTTP-запросов;
- `beautifulsoup4) — пакет для разбора HTML и поиска элементов в документе;
- `mcp) — пакет с реализацией компонентов протокола Model Context Protocol;
- `pytest) — инструмент для запуска автоматических тестов.

**HTTP** (*Hypertext Transfer Protocol*) — протокол передачи данных, который используется, в частности, при загрузке веб-страниц и обращении к веб-сервисам.

**HTML** (*HyperText Markup Language*) — язык разметки, описывающий структуру веб-страницы: заголовки, абзацы, ссылки и другие элементы.

**Тест** (*test*) — проверка, которая помогает убедиться, что программа ведёт себя ожидаемым образом. Автоматический тест можно запускать многократно после изменений кода.

### 3.3. Стандартная и сторонняя библиотеки

В Python есть **стандартная библиотека** — набор модулей, поставляемых вместе с Python. Например, `json), `pathlib), `logging) и `urllib). Для их использования обычно не нужно выполнять `pip install).

**Сторонняя библиотека** — библиотека, которую устанавливают отдельно. Например, `httpx) не является частью стандартной библиотеки, поэтому её нужно установить в выбранное Python-окружение.

Важно не путать:
- `import json) — подключение модуля из стандартной библиотеки;
- `import httpx) — подключение сторонней библиотеки, которую предварительно нужно установить;
- `pip install httpx) — команда терминала для установки пакета. Это не строка Python-кода, её не вставляют в файл `.py).

## 4. Что такое pip

**pip** — стандартный инструмент установки и управления пакетами Python. Он скачивает пакеты из настроенного источника пакетов и устанавливает их в выбранное Python-окружение.

Команда:

~~~powershell
python -m pip --version
~~~

проверяет, доступен ли pip для того интерпретатора Python, который запускается командой `python).

Почему мы используем форму `python -m pip), а не только `pip)?

- `python) выбирает интерпретатор;
- `-m) просит Python запустить указанный модуль как программу;
- `pip) — модуль установщика пакетов.

Таким образом, команда явно связывает pip с тем интерпретатором, который указан перед `-m). Это снижает риск установить библиотеку в один Python, а запускать программу через другой.

Проверьте версию Python:

~~~powershell
python --version
~~~

Затем проверьте pip:

~~~powershell
python -m pip --version
~~~

Версии на вашем компьютере могут отличаться от примеров в интернете — это нормально. Для курса важно, чтобы команда выполнялась без ошибки и вы понимали, к какому окружению она относится.

### 4.1. Установка одного пакета

Например:

~~~powershell
python -m pip install httpx
~~~

Команда просит pip установить пакет `httpx) в окружение текущего интерпретатора. Для установки может понадобиться подключение к источнику пакетов.

Не выполняйте установку вслепую, если не понимаете, какой Python используется. Сначала активируйте виртуальное окружение, как описано ниже.

### 4.2. Обновление pip

Внутри активированного виртуального окружения можно выполнить:

~~~powershell
python -m pip install --upgrade pip
~~~

Флаг `--upgrade) просит установить более новую доступную версию пакета. Для учебной работы обновление pip обычно необязательно, если он работает корректно; команда приведена, чтобы вы умели читать такие инструкции.

## 5. Зачем нужно виртуальное окружение

Представим, что вы пишете два проекта:
- первый использует одну версию библиотеки;
- второй требует другую версию той же библиотеки.

Если все пакеты устанавливать в общий Python, проекты могут начать конфликтовать. Обновление библиотеки ради одного проекта способно нарушить работу другого.

**Виртуальное окружение** (*virtual environment*) — отдельная папка с изолированным набором установленных Python-пакетов и настройками запуска для конкретного проекта. Оно позволяет держать зависимости разных проектов отдельно.

Для нашего курса это особенно важно: учебный MCP-сервер будет использовать сторонние библиотеки, а другие ваши Python-проекты могут требовать совершенно иной набор зависимостей.

Преимущества виртуального окружения:
- зависимости одного проекта не смешиваются с зависимостями другого;
- можно восстановить окружение по списку пакетов;
- проще воспроизводить ошибки и тестировать код;
- меньше риск случайно изменить глобальную установку Python;
- понятнее, где установлены библиотеки.

Сам код проекта обычно не хранится внутри виртуального окружения. Виртуальное окружение содержит интерпретаторные файлы и установленные пакеты; ваши исходники находятся в `src), `lessons), `tests) и других папках проекта.

## 6. Создаём виртуальное окружение в Windows

Все команды ниже выполняются в терминале PowerShell в папке проекта `cherkashin_web_search).

### 6.1. Откройте папку проекта

В VS Code откройте папку репозитория через меню **File → Open Folder**. Затем откройте терминал: **Terminal → New Terminal**.

Проверьте текущую папку:

~~~powershell
Get-Location
~~~

Команда PowerShell `Get-Location) показывает текущий путь. Убедитесь, что это именно папка вашего проекта, а не случайная другая директория.

Можно посмотреть файлы и папки:

~~~powershell
Get-ChildItem
~~~

Это команда PowerShell для вывода содержимого текущей папки. Её часто сокращают до `ls) или `dir), но в учебных материалах будем использовать понятное имя `Get-ChildItem).

### 6.2. Создайте окружение

Выполните:

~~~powershell
python -m venv .venv
~~~

Разберём команду по частям:
- `python) запускает выбранный интерпретатор Python;
- `-m venv) запускает стандартный модуль `venv), предназначенный для создания виртуальных окружений;
- `.venv) — имя папки, куда будет создано окружение.

Точка в начале имени — часть имени папки, а не оператор Python. Название `.venv) является соглашением: по имени легко понять, что это окружение проекта. Можно было бы выбрать другое имя, но лучше использовать одно и то же во всех командах курса.

После выполнения в проекте появится папка `.venv). Команда может не вывести никакого текста при успешном завершении — это нормально. Проверьте наличие папки через `Get-ChildItem).

Если папка `.venv) уже существует, не создавайте другое окружение с другим именем без причины. Сначала выясните, можно ли использовать имеющееся.

### 6.3. Активируйте окружение в PowerShell

Выполните:

~~~powershell
.\.venv\Scripts\Activate.ps1
~~~

В этом пути:
- `.) означает «начать путь из текущей папки»;
- `.venv) — папка виртуального окружения;
- `Scripts) — папка с командами активации в Windows;
- `Activate.ps1) — сценарий активации для PowerShell.

После активации в начале приглашения терминала обычно появляется `(.venv)). Например:

~~~text
(.venv) PS D:\Projects\cherkashin_web_search>
~~~

Путь у вас будет собственным. Главное — увидеть префикс `(.venv)) и проверить, что используется нужный Python.

Проверьте интерпретатор:

~~~powershell
python --version
python -m pip --version
Get-Command python
~~~

Последняя команда показывает, какая команда `python) будет вызвана в PowerShell. После активации путь должен указывать на интерпретатор внутри `.venv).

### 6.4. Если PowerShell запрещает запуск сценария

На некоторых компьютерах политика выполнения PowerShell может блокировать сценарий активации. Вы увидите сообщение о том, что выполнение сценариев отключено или запрещено.

Не меняйте системную политику без необходимости. Сначала можно активировать окружение через другой терминал VS Code, например **Command Prompt (cmd)**, где команда будет такой:

~~~bat
.venv\Scripts\activate.bat
~~~

Другой вариант — использовать Python из окружения напрямую, не активируя его:

~~~powershell
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip --version
~~~

Активация — удобство для терминала, но не обязательное условие существования окружения. Если потребуется менять политику PowerShell, сначала изучите ограничения вашего компьютера и согласуйте их с администратором, если это рабочее устройство.

### 6.5. Деактивация

Когда закончите работу с окружением, можно выполнить:

~~~powershell
deactivate
~~~

Команда возвращает терминал к обычному окружению. Она не удаляет папку `.venv) и не удаляет установленные в ней пакеты.

Для следующей работы достаточно снова активировать окружение.

## 7. Устанавливаем зависимости проекта

**Зависимость** (*dependency*) — внешний пакет или компонент, который нужен программе для работы. Если код импортирует `httpx), то библиотека `httpx) становится зависимостью проекта.

В репозитории курса есть файл `requirements.txt). Это текстовый список пакетов, которые нужны проекту. Сейчас в нём перечислены:

~~~text
httpx
beautifulsoup4
mcp
pytest
~~~

Рассмотрим назначение каждого:
- `httpx) — для будущих HTTP-запросов к веб-страницам и поисковым сервисам;
- `beautifulsoup4) — для разбора HTML и извлечения текста и элементов;
- `mcp) — для создания сервера и инструментов Model Context Protocol;
- `pytest) — для запуска автоматических тестов.

На этом уроке мы только устанавливаем пакеты. Реальное применение `httpx) и `beautifulsoup4) подробно разберём в следующих уроках.

### 7.1. Установка из requirements.txt

Убедитесь, что виртуальное окружение активировано и вы находитесь в корневой папке проекта. Выполните:

~~~powershell
python -m pip install -r requirements.txt
~~~

Объяснение:
- `python -m pip) запускает pip через текущий интерпретатор;
- `install) указывает, что нужно установить пакеты;
- `-r) означает прочитать список требований из файла;
- `requirements.txt) — имя этого файла.

**Преимущество:** вместо ручной установки каждой библиотеки достаточно одной команды. Если проект разворачивается на другом компьютере, можно повторить установку по тому же списку.

Установка может занять некоторое время. Нужен доступ к источнику пакетов. Если команда завершилась ошибкой, прочитайте последние строки сообщения: они часто содержат причину — например, отсутствие подключения, несовместимость версии Python или ошибку доступа.

### 7.2. Проверяем установленные пакеты

Выполните:

~~~powershell
python -m pip list
~~~

Команда покажет пакеты, установленные в активном окружении. Список будет длиннее четырёх строк, потому что у библиотек могут быть собственные зависимости.

Можно проверить конкретный пакет:

~~~powershell
python -m pip show httpx
~~~

Команда выведет сведения о пакете, в том числе версию и место установки. Путь установки должен соответствовать окружению проекта, если вы активировали `.venv).

### 7.3. Проверяем импорты

Создайте временный файл `check_dependencies.py) в корне проекта:

~~~python
import httpx
import bs4
import mcp
import pytest

print("Импорты библиотек выполнены успешно")
~~~

Запустите:

~~~powershell
python check_dependencies.py
~~~

Если всё установлено корректно и пакеты доступны выбранному интерпретатору, ожидаемый результат:

~~~text
Импорты библиотек выполнены успешно
~~~

Почему мы пишем `import bs4), а устанавливаем `beautifulsoup4)? Имя пакета для установки и имя модуля для импорта не всегда совпадают. Это нормальная ситуация в экосистеме Python.

Если проверка падает на импорте, не нужно сразу переустанавливать Python. Проверьте, что окружение активировано, и выполните `python -m pip show имя_пакета) для соответствующей библиотеки. После проверки временный файл можно удалить или перенести в отдельные учебные примеры.

## 8. Файл requirements.txt и воспроизводимость

**Воспроизводимость** (*reproducibility*) — возможность повторить установку и получить окружение с ожидаемыми компонентами, чтобы программа запускалась одинаково предсказуемо.

Файл `requirements.txt) перечисляет зависимости проекта. В простом учебном варианте пакет может быть указан без версии:

~~~text
httpx
beautifulsoup4
mcp
pytest
~~~

Это означает, что pip может установить доступную совместимую версию каждого пакета. Такой подход прост, но со временем новые версии библиотек могут изменить поведение или требования.

Для более строгой воспроизводимости зависимости фиксируют версиями, например:

~~~text
some-package==1.2.3
~~~

Здесь `==) в файле требований означает, что требуется конкретная версия пакета. Не следует копировать случайные номера версий из чужого примера: версии нужно выбирать после проверки совместимости и тестирования проекта.

В нашем курсе сначала важно понять механизм установки. Когда мы начнём интеграцию с HTTP и MCP и проверим совместимость, можно будет зафиксировать конкретные версии в соответствии с реальными результатами тестирования.

### 8.1. Обновление списка зависимостей

Если проекту понадобится новая библиотека, обычно выполняют такие шаги:
1. активируют окружение проекта;
2. устанавливают пакет через `python -m pip install имя-пакета);
3. проверяют импорт и работу;
4. обновляют `requirements.txt), чтобы зависимость не потерялась для другого компьютера.

Не нужно добавлять в список любую библиотеку, которую вы установили для разового эксперимента. В файл проекта должны попадать зависимости, действительно необходимые для запуска или тестирования проекта.

## 9. Папка .venv и файл .gitignore

**Git** — система контроля версий: она хранит историю изменений исходников и позволяет сравнивать версии проекта. Репозиторий курса находится на GitHub, поэтому важно понимать, какие файлы следует сохранять в истории.

Папку `.venv) обычно не отправляют в Git. Причины:
- она может занимать много места;
- содержит множество файлов, созданных автоматически;
- зависит от операционной системы и конфигурации Python;
- её можно восстановить по `requirements.txt).

Для исключения файлов используется `.gitignore) — текстовый файл с правилами, указывающими Git, какие файлы и папки не следует включать в обычное отслеживание.

Пример правил:

~~~gitignore
.venv/
__pycache__/
*.py[cod]
.env
.pytest_cache/
~~~

Что означают правила:
- `.venv/) исключает папку виртуального окружения;
- `__pycache__/) исключает каталоги с автоматически созданными файлами байткода Python;
- `*.py[cod]) исключает файлы с расширениями `.pyc), `.pyo) и `.pyd);
- `.env) исключает файл локальных переменных окружения, в котором могут находиться конфиденциальные настройки;
- `.pytest_cache/) исключает служебный кэш pytest.

**Кэш** (*cache*) — временно сохранённые данные, которые помогают ускорить повторные операции. Кэш обычно не является исходным кодом проекта.

Важно: `.gitignore) не удаляет уже отслеживаемые Git файлы автоматически. Он влияет на файлы, которые ещё не отслеживаются, и на некоторые операции добавления. Если папка `.venv) уже была закоммичена, одного добавления правила может быть недостаточно для прекращения её отслеживания.

### 9.1. Не помещайте секреты в репозиторий

Если позже понадобится API-ключ поискового сервиса, пароль или другой секрет, не записывайте его в исходный код и не отправляйте в публичный репозиторий. Конфиденциальные значения обычно хранят в переменных окружения или локальных конфигурационных файлах, которые исключены из Git.

На этом уроке API-ключи не используются, а реальные сетевые запросы мы пока не отправляем.

### `__init__.py`

Файл, обозначающий пакет в традиционной структуре Python. На этом этапе он может оставаться пустым или содержать короткий комментарий.

Когда проект станет больше, мы будем держать настройки отдельно от сетевой логики, а тесты — отдельно от кода приложения. Тогда проще проверить отдельную часть, заменить реализацию или найти ошибку.

## 11. Практика: импортируем настройки из пакета проекта

Теперь применим изученное к реальному расположению файлов курса.

В репозитории уже существует файл:

~~~text
src/web_search_mcp/config.py
~~~

Его содержимое на текущем этапе:

~~~python
"""Начальные настройки проекта. Сетевой логики здесь пока нет."""

SERVER_NAME = "web-search-mcp"
DEFAULT_TIMEOUT_SECONDS = 15
DEFAULT_MAX_SEARCH_RESULTS = 5
DEFAULT_MAX_PAGE_CHARS = 12_000
~~~

Первая строка — это **строка документации** (*docstring*). Она кратко описывает назначение модуля. Три двойные кавычки используются для многострочных строк и часто применяются для описания модулей, классов и функций. В этом примере текст занимает одну строку, но оформлен как docstring.

Символ подчёркивания в имени `DEFAULT_TIMEOUT_SECONDS) — часть имени переменной. Он разделяет слова и улучшает читаемость.

Запись `12_000) — целое число 12000. В Python подчёркивания можно использовать в числовых литералах для удобства чтения; они не изменяют числовое значение.

Чтобы проверить импорт, создайте временный файл `check_config.py) в корне репозитория:

~~~python
from src.web_search_mcp.config import (
    SERVER_NAME,
    DEFAULT_TIMEOUT_SECONDS,
    DEFAULT_MAX_SEARCH_RESULTS,
    DEFAULT_MAX_PAGE_CHARS,
)

print(f"Имя сервера: {SERVER_NAME}")
print(f"Тайм-аут: {DEFAULT_TIMEOUT_SECONDS} секунд")
print(f"Максимум результатов: {DEFAULT_MAX_SEARCH_RESULTS}")
print(f"Максимальная длина страницы: {DEFAULT_MAX_PAGE_CHARS}")
~~~

Здесь используется **импорт с переносом строки** внутри круглых скобок. Круглые скобки позволяют разместить перечень имён на нескольких строках, не используя символ продолжения строки. Это повышает читаемость длинного импорта.

Запустите из корня репозитория:

~~~powershell
python check_config.py
~~~

В ожидаемом выводе должны быть значения из `config.py):

~~~text
Имя сервера: web-search-mcp
Тайм-аут: 15 секунд
Максимум результатов: 5
Максимальная длина страницы: 12000
~~~

В зависимости от структуры пакета и способа запуска импортов, для учебных проверок предпочтительно запускать команду из корня репозитория. Позже, когда будем настраивать установку самого проекта, разберём более строгую схему запуска пакета. Не нужно ради этого сейчас менять исходники приложения.

После проверки временный файл `check_config.py) можно удалить. Это демонстрационный файл, а не обязательная часть приложения.

## 12. Частые ошибки и способы их исправления

### Ошибка 1. `ModuleNotFoundError`

Пример сообщения:

~~~text
ModuleNotFoundError: No module named 'httpx'
~~~

Это означает, что выбранный интерпретатор не нашёл модуль с таким именем.

Проверьте:
1. активировано ли окружение `.venv);
2. установлен ли пакет в этом окружении;
3. запускается ли программа тем же интерпретатором, куда установлен пакет.

Команды проверки:

~~~powershell
python -m pip show httpx
python -c "import sys; print(sys.executable)"
~~~

Первая команда показывает сведения о пакете. Вторая печатает путь к используемому интерпретатору. Если пакет не установлен, активируйте окружение и выполните установку из `requirements.txt).

### Ошибка 2. Установили пакет, но Python его не видит

Частая причина — установка прошла в один Python, а запуск производится другим.

Для установки и запуска используйте один и тот же способ. Например, после активации окружения:

~~~powershell
python -m pip install -r requirements.txt
python check_dependencies.py
~~~

Не запускайте случайный глобальный `pip) и не предполагайте, что все установленные пакеты доступны во всех окружениях.

### Ошибка 3. Неверная папка при запуске

Если терминал находится не в корне проекта, команда может не найти файл `requirements.txt) или учебный скрипт.

Проверьте:

~~~powershell
Get-Location
Get-ChildItem
~~~

Перейдите в папку проекта командой `Set-Location) или откройте правильную папку в VS Code.

### Ошибка 4. Не удаётся активировать окружение

Если PowerShell блокирует `Activate.ps1), прочитайте сообщение об ошибке. Для проверки можно запустить интерпретатор напрямую:

~~~powershell
.\.venv\Scripts\python.exe --version
~~~

Если команда работает, окружение создано. Проблема может быть именно в запуске сценария активации, а не в Python.

### Ошибка 5. Импорт собственного модуля не работает

Проверьте:
- правильное ли имя файла и модуля;
- запускаете ли программу из ожидаемой папки;
- не назвали ли свой файл именем стандартного модуля, например `json.py) или `httpx.py).

Если файл вашего проекта называется так же, как сторонний или стандартный модуль, Python может попытаться импортировать ваш файл вместо нужной библиотеки. Для учебных скриптов используйте описательные имена вроде `check_dependencies.py).

### Ошибка 6. В Git появилась папка .venv

Проверьте содержимое `.gitignore). Убедитесь, что правило `.venv/) есть в нём. Если папка уже отслеживается Git, не удаляйте её вручную без понимания состояния репозитория. Сначала выясните, отслеживается ли она, и только потом исправляйте правила.

- пакет — организованная группа модулей;
- библиотека предоставляет готовые функции и компоненты;
- `import) позволяет использовать код из других модулей;
- pip устанавливает сторонние пакеты;
- виртуальное окружение отделяет зависимости проекта от других проектов;
- `requirements.txt) хранит список необходимых пакетов;
- `.gitignore) исключает служебные и локальные файлы из обычного отслеживания Git.

Для нашего проекта это означает, что теперь мы можем подготовить изолированное окружение, установить библиотеки для HTTP-запросов, разбора HTML и MCP и организовывать код по отдельным модулям.

**В следующем уроке № 7** начнём разбирать HTTP-запросы и обработку ошибок. Научимся обращаться к веб-адресу с помощью `httpx), устанавливать тайм-аут и корректно реагировать на сетевые проблемы. Это будет первый шаг от условных результатов поиска к реальному взаимодействию с веб-страницами.
