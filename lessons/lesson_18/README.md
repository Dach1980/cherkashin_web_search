# Урок 18. Асинхронность и параллельные веб-запросы

> Дополнительный урок. Основной курс состоит из уроков 1–17. Этот материал нужен, если вы хотите ускорить операции, которые большую часть времени ждут ответа от сети.

## Цель урока

Наш MCP-сервер выполняет две сетевые задачи: ищет страницы и загружает их содержимое. Сетевые запросы часто тратят много времени не на вычисления, а на ожидание ответа удалённого сервера. Если выполнять несколько независимых запросов строго по очереди, общее время может заметно увеличиться.

В этом уроке разберём асинхронность Python, конкурентное выполнение нескольких сетевых операций, ограничения количества одновременных запросов и обработку ошибок. Напишем отдельный учебный пример на библиотеке HTTPX, которая уже указана в requirements.txt проекта.

**Важное отличие:** асинхронность не делает один запрос автоматически быстрее и не означает, что Python одновременно исполняет все инструкции на разных процессорных ядрах. Она позволяет программе переключаться на другую работу, пока текущая операция ожидает сеть.

## 1. Иностранные термины

- **Asynchronous programming — асинхронное программирование.** Организация программы, при которой во время ожидания одной операции можно выполнять другую готовую работу.
- **Synchronous — синхронный.** Вызвав операцию, программа ждёт её завершения, прежде чем перейти дальше.
- **Async / await.** Ключевые слова Python для определения асинхронных функций и ожидания асинхронных операций.
- **Concurrency — конкурентность.** Несколько задач продвигаются в течение одного периода времени, чередуя выполнение. Это не обязательно одновременное исполнение на разных ядрах.
- **Parallelism — параллелизм.** Фактическое выполнение нескольких вычислений в один и тот же момент, например на разных ядрах процессора.
- **I/O-bound — задача, ограниченная вводом-выводом.** Работа, где время в основном уходит на сеть, диск или другое устройство, а не на вычисления процессора.
- **CPU-bound — задача, ограниченная процессором.** Работа, где основное время уходит на вычисления.
- **Coroutine — корутина.** Асинхронная функция, объявленная через async def; её выполнение может приостанавливаться и продолжаться.
- **Event loop — цикл событий.** Механизм, который управляет запуском и возобновлением асинхронных задач.
- **Task — задача.** Объект, позволяющий циклу событий отслеживать и планировать выполнение корутины.
- **HTTP client — HTTP-клиент.** Библиотека, которая отправляет HTTP-запросы и принимает ответы.
- **Connection pool — пул соединений.** Набор соединений, которые клиент может повторно использовать, вместо постоянного создания новых.
- **Semaphore — семафор.** Механизм ограничения количества задач, одновременно проходящих через определённый участок кода.
- **Rate limit — ограничение частоты запросов.** Правило, сколько запросов разрешено выполнять за определённый период.
- **Timeout — тайм-аут.** Максимальное время ожидания операции.
- **Exception — исключение.** Объект, сигнализирующий о возникшей ошибке.
- **Resource — ресурс.** Объект, который нужно корректно использовать и освобождать, например HTTP-клиент или сетевое соединение.
- **Backpressure — обратное давление.** Ограничение поступления новых задач, когда система или удалённый сервис не успевает их обслуживать.
- **Throughput — пропускная способность.** Количество запросов или задач, которые система успешно обрабатывает за единицу времени.
- **Latency — задержка.** Время от отправки запроса до получения результата.
- **Benchmark — сравнительное измерение производительности.** Измерение времени или пропускной способности для сопоставления вариантов.

## 2. Синхронный подход: почему он может быть медленным

Представим, что нужно получить три страницы, и каждый сервер отвечает примерно за две секунды.

Синхронный вариант:
1. Отправляем запрос A и ждём две секунды.
2. Отправляем запрос B и ждём две секунды.
3. Отправляем запрос C и ждём две секунды.

Общее время ожидания может приблизиться к шести секундам. В асинхронном варианте можно начать все три запроса и ждать их вместе. Если серверы отвечают примерно за две секунды, общий срок может оказаться ближе к двум секундам плюс накладные расходы.

Это иллюстрация, а не обещание конкретной скорости. Реальный результат зависит от сети, сервера, ограничений частоты, DNS, TLS, объёма ответа и других факторов. Некоторые сайты намеренно ограничивают параллельные запросы.

## 3. Когда асинхронность полезна

Асинхронность обычно полезна для I/O-bound операций:
- одновременно получить несколько страниц из результатов поиска;
- выполнять независимые HTTP-запросы, пока другие ожидают сеть;
- обслуживать несколько запросов без создания отдельного потока для каждого ожидания.

Она не всегда полезна:
- если работа в основном вычислительная;
- если задача состоит из коротких операций, где накладные расходы больше выигрыша;
- если удалённый сайт ограничивает частоту запросов;
- если код усложняется, а измеримого ускорения нет.

Сначала нужно определить узкое место, затем оптимизировать. Для одного запроса переход с синхронного на асинхронный API не гарантирует меньшую задержку.

## 4. Новые конструкции Python

### async def

Объявляет асинхронную функцию — корутину. В отличие от обычной функции, её вызов возвращает объект корутины, а не сразу готовое значение. Чтобы выполнить корутину, её нужно ожидать через await или передать в механизм запуска задач.

### await

Приостанавливает выполнение текущей корутины, пока ожидаемая асинхронная операция не завершится. В это время цикл событий может запускать другие готовые задачи.

await нельзя произвольно поставить перед любой функцией. Ожидаемое значение должно поддерживать асинхронный протокол, например быть корутиной или подходящим объектом ожидания.

### async with

Асинхронный аналог контекстного менеджера with. Он нужен для ресурсов, у которых открытие и закрытие могут требовать асинхронных операций. В примере HTTPX-клиент создаётся один раз для группы запросов и закрывается автоматически при выходе из блока.

### asyncio.gather()

Запускает несколько переданных корутин совместно и возвращает результаты в порядке переданных корутин, а не обязательно в порядке завершения. Это удобно, когда все результаты нужны вызывающему коду.

Если одна корутина выбрасывает необработанное исключение, обычный вызов gather может передать это исключение вызывающему коду. Поэтому в примере каждая загрузка самостоятельно перехватывает сетевые ошибки и возвращает результат с полем error.

### asyncio.Semaphore()

Ограничивает число корутин, которые одновременно находятся внутри защищённого участка. Например, семафор со значением 3 не позволяет более чем трём задачам одновременно выполнять HTTP-запрос в этом участке.

Это важно для сайтов и собственного компьютера: без ограничений большой список URL может породить слишком много одновременных соединений.

### async with semaphore

Перед входом в блок корутина ждёт свободный слот семафора. При выходе слот освобождается автоматически, в том числе если внутри блока возникло исключение. Это безопаснее, чем вручную увеличивать и уменьшать счётчик.

## 5. Пример: ограниченная параллельная загрузка страниц

Файл примера: examples/lesson18_async_fetch.py.

Пример использует библиотеку httpx, которая уже присутствует в зависимостях проекта. Запускайте его только с известными публичными адресами. Это учебный пример, а не готовая замена защищённой функции web_fetch: производственный MCP-сервер должен сохранять URL-валидацию, защиту от SSRF, проверку перенаправлений, ограничение размера ответа и правила извлечения текста из уроков 9, 11 и 17.

    import asyncio

    import httpx


    MAX_CONCURRENT_REQUESTS = 3
    REQUEST_TIMEOUT_SECONDS = 10.0


    async def fetch_status(
        client: httpx.AsyncClient,
        url: str,
        semaphore: asyncio.Semaphore,
    ) -> dict[str, str | int | None]:
        """Получить статус или вернуть диагностическую ошибку."""
        async with semaphore:
            try:
                response = await client.get(url)
                return {
                    "url": url,
                    "status_code": response.status_code,
                    "error": None,
                }
            except httpx.TimeoutException:
                return {
                    "url": url,
                    "status_code": None,
                    "error": "timeout",
                }
            except httpx.HTTPError as error:
                return {
                    "url": url,
                    "status_code": None,
                    "error": type(error).__name__,
                }


    async def main() -> None:
        urls = [
            "https://example.com/",
            "https://www.python.org/",
            "https://httpbin.org/status/404",
        ]

        limits = httpx.Limits(
            max_connections=MAX_CONCURRENT_REQUESTS,
            max_keepalive_connections=MAX_CONCURRENT_REQUESTS,
        )
        timeout = httpx.Timeout(REQUEST_TIMEOUT_SECONDS)
        semaphore = asyncio.Semaphore(MAX_CONCURRENT_REQUESTS)

        async with httpx.AsyncClient(
            timeout=timeout,
            limits=limits,
            follow_redirects=True,
            headers={"User-Agent": "Lesson18AsyncExample/1.0"},
        ) as client:
            results = await asyncio.gather(
                *(fetch_status(client, url, semaphore) for url in urls)
            )

        for result in results:
            print(result)


    if __name__ == "__main__":
        asyncio.run(main())

## 6. Подробный разбор кода

### Импорт библиотек

import asyncio подключает стандартный модуль Python для асинхронного программирования. Он предоставляет цикл событий, семафоры, сбор результатов и другие инструменты.

import httpx подключает HTTPX — внешнюю библиотеку для HTTP-запросов. Её асинхронный клиент поддерживает await.

### Константы

MAX_CONCURRENT_REQUESTS = 3 задаёт лимит одновременных запросов. Заглавные буквы — распространённое соглашение Python для имён констант, то есть значений, которые по замыслу программы не меняют в ходе работы. Сам язык не запрещает их переопределять.

REQUEST_TIMEOUT_SECONDS = 10.0 задаёт тайм-аут в секундах. Значение 10.0 имеет тип float — число с плавающей точкой.

### Объявление асинхронной функции

async def fetch_status(...) определяет корутину, которая принимает HTTP-клиент, URL и семафор. Аннотация client: httpx.AsyncClient описывает ожидаемый тип клиента; url: str — строку URL; semaphore: asyncio.Semaphore — семафор.

Аннотация -> dict[str, str | int | None] описывает словарь, значения которого могут быть строками, целыми числами или None. Символ | в аннотации типов означает объединение допустимых типов. Это не оператор объединения словарей в данном месте кода. None означает отсутствие значения, например когда HTTP-статус не получен.

### Ограничение параллельности

async with semaphore ждёт свободный слот и занимает его на время блока. Если одновременно уже выполняются три запроса, следующая корутина дождётся освобождения слота. При выходе из блока слот освободится автоматически.

В данном примере async with semaphore включает не только отправку запроса, но и обработку результата или исключения. Поэтому лимит относится ко всему защищённому участку.

### Асинхронный HTTP-запрос

response = await client.get(url) отправляет GET-запрос. Ключевое слово await позволяет текущей корутине уступить управление, пока сеть ожидает ответ. Цикл событий в это время может продолжать другие задачи.

Мы не вызываем синхронный httpx.get(), поскольку он блокировал бы поток выполнения во время ожидания сети. В этом примере используется именно асинхронный клиент httpx.AsyncClient.

### Словарь результата

return {...} возвращает структурированный результат: URL, статус и ошибку. Если запрос завершился, error равен None. Если возникла ошибка, статус не получен и записывается причина.

Такой формат удобнее для дальнейшей обработки, чем одна строка, в которой смешаны адрес, статус и описание ошибки.

### Обработка исключений

except httpx.TimeoutException перехватывает тайм-ауты HTTPX и возвращает категорию timeout.

except httpx.HTTPError as error перехватывает другие ошибки уровня HTTPX. Конструкция as error сохраняет объект исключения в переменную, чтобы можно было узнать тип ошибки.

type(error).__name__ получает имя класса исключения, например ConnectError. Для учебной диагностики этого достаточно; в полноценном журнале не следует бездумно записывать чувствительные URL, токены или полное содержимое запросов.

**Почему мы не используем просто except:** широкий перехват всех исключений может скрыть ошибки программирования, такие как неправильное обращение к переменной. Лучше перехватывать ожидаемые типы ошибок. В производственном коде также следует продумать отмену задач и другие исключения времени выполнения.

### Асинхронная главная функция

В main() создаётся список URL. В примере три публичных адреса для демонстрации разных ответов. Один из них запрашивает статус 404 специально: HTTP 404 сам по себе не является сетевым исключением, поэтому его код появится в поле status_code.

### Пул соединений

httpx.Limits(...) задаёт лимиты соединений клиента. Семафор ограничивает число запросов в нашем коде, а настройки клиента ограничивают число сетевых соединений. Эти механизмы дополняют друг друга, но не заменяют друг друга.

httpx.Timeout(REQUEST_TIMEOUT_SECONDS) задаёт ограничения ожидания сетевых операций. Тайм-ауты защищают программу от бесконечного ожидания, хотя разные фазы запроса могут иметь свои особенности.

### Создание клиента и перенаправления

async with httpx.AsyncClient(...) as client создаёт один клиент на все URL. Повторное использование клиента позволяет HTTPX переиспользовать соединения, когда это возможно. При выходе из блока клиент закрывается.

follow_redirects=True разрешает HTTPX следовать перенаправлениям. **В производственном MCP-сервере недостаточно просто включить это значение:** каждый адрес перенаправления должен повторно проходить проверку безопасности, чтобы нельзя было перейти с публичного URL на локальный или внутренний адрес. В учебном примере используются фиксированные известные адреса, но это ограничение обязательно нужно учитывать при обработке пользовательских URL.

### asyncio.gather() и выражение-генератор

    results = await asyncio.gather(
        *(fetch_status(client, url, semaphore) for url in urls)
    )

Здесь сразу несколько важных конструкций.

- for url in urls перебирает URL.
- fetch_status(...) создаёт корутину для каждого адреса.
- Выражение ( ... for url in urls) — генераторное выражение, которое создаёт значения по мере перебора.
- Символ * перед генераторным выражением — **распаковка аргументов**. Он передаёт каждый полученный объект как отдельный позиционный аргумент функции asyncio.gather().
- asyncio.gather(...) собирает выполнение корутин и возвращает результаты.
- await ждёт завершения общей операции.

Распаковка * полезна, когда количество URL заранее неизвестно: не нужно вручную писать отдельный вызов для каждого адреса. При этом gather() возвращает результаты в порядке входных корутин, а не обязательно в порядке, в котором серверы ответили.

### Запуск цикла событий

asyncio.run(main()) создаёт и запускает цикл событий для асинхронной функции main(), а после завершения корректно закрывает его. Это стандартный способ запустить асинхронную программу верхнего уровня в обычном Python-скрипте.

Условие if __name__ == "__main__": гарантирует, что запуск произойдёт при непосредственном выполнении файла, но не при его импорте как модуля.

## 8. Важные ограничения и безопасность

1. **Не отправляйте сотни запросов одновременно.** Начните с малого лимита и увеличивайте его только после измерений и проверки правил сайта.
2. **Сохраняйте URL-валидацию.** Для пользовательских адресов проверяйте схему, DNS/IP, запрет внутренних адресов и каждый редирект. Это защита от SSRF — Server-Side Request Forgery, атаки, при которой злоумышленник пытается заставить сервер обратиться к недоступному извне внутреннему ресурсу.
3. **Ограничивайте размер ответа.** Тайм-аут не предотвращает загрузку гигантского файла. Нужны отдельные лимиты объёма данных и длины извлечённого текста.
4. **Обрабатывайте HTTP-статусы.** Ответ 404 или 429 может быть корректно полученным HTTP-ответом, но не успешным результатом поиска.
5. **Учитывайте правила сервиса.** Параллельность не должна превращаться в обход ограничений частоты.
6. **Не запускайте вложенные циклы событий.** Если функция уже выполняется внутри асинхронного приложения, обычно нужно вызвать или ожидать корутину, а не запускать внутри неё новый asyncio.run().
7. **Не считайте параллельность всегда быстрее.** Измеряйте задержку, количество ошибок и пропускную способность.
8. **Не переписывайте весь MCP-сервер на async без необходимости.** Изменение архитектуры требует отдельной проверки совместимости MCP SDK и тестов. Учебный пример изолирован от основного сервера именно для того, чтобы безопасно изучить механику.

## 9. Практические задания

## Итог урока

Асинхронность помогает эффективнее использовать время ожидания сети, когда нужно получить несколько независимых страниц. В Python ключевые элементы этого подхода — async def, await, async with, asyncio.gather() и asyncio.Semaphore.

Но скорость не важнее корректности: необходимо ограничивать параллельность, задавать тайм-ауты, обрабатывать ошибки и сохранять все проверки безопасности URL и перенаправлений. Этот урок — дополнительный и не меняет базовую архитектуру MCP-сервера без отдельного решения и тестирования.
