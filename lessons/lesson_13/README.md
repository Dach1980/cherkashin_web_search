# Урок № 13. Конфигурация, переменные окружения и логирование

## 1. Цель урока

В предыдущих уроках мы создали Python MCP-сервер для LM Studio с инструментами search_web и fetch_web_page. В проекте уже есть настройки: тайм-аут HTTP-запроса, количество результатов поиска, максимальная длина текста, количество перенаправлений и максимальный размер HTTP-ответа.

Если все значения записаны непосредственно в исходном коде, изменение параметров требует редактирования программы. Это неудобно, когда один компьютер нуждается в тайм-ауте 15 секунд, другой — 25 секунд, а разработчику иногда нужно видеть подробные диагностические сообщения. Поэтому разделим обязанности: **код определяет алгоритм, конфигурация задаёт параметры, логирование помогает понять, что происходило при выполнении**.

Результат урока: настройки читаются из переменных окружения, некорректные значения отклоняются, журнал настроен на стандартный поток ошибок, а протокольный поток MCP остаётся чистым.

Важно: сохранение изменений и успешный импорт кода сами по себе не доказывают, что интеграция с LM Studio фактически проверена. Для этого нужно запустить сервер и вызвать инструменты из LM Studio.

## 2. Иностранные термины

- **Configuration (конфигурация)** — параметры, определяющие поведение программы: тайм-ауты, лимиты и уровень журнала.
- **Environment variable (переменная окружения)** — именованное значение, которое операционная система передаёт процессу. Например, WEB_TIMEOUT_SECONDS=20.
- **Environment (окружение)** — условия, в которых работает процесс: переменные, рабочий каталог и доступные команды. Не путайте это с виртуальным окружением Python .venv, которое изолирует пакеты.
- **.env file** — текстовый файл с настройками. Python не загружает его автоматически: нужен дополнительный код или библиотека вроде python-dotenv. В этом уроке мы обойдёмся без неё.
- **Logging (логирование)** — запись диагностических событий во время работы программы.
- **Log level (уровень журнала)** — важность сообщения: DEBUG — подробности разработки; INFO — обычные события; WARNING — неожиданная ситуация; ERROR — операция не выполнена; CRITICAL — критическая проблема.
- **Logger (регистратор)** — объект, создающий записи журнала.
- **Handler (обработчик)** — компонент, направляющий журнал в поток или файл.
- **Formatter (форматировщик)** — правило оформления записи: время, уровень, имя модуля, сообщение.
- **stdout** — стандартный поток вывода, обычно используемый print().
- **stderr** — отдельный стандартный поток ошибок и диагностики.
- **MCP (Model Context Protocol)** — протокол взаимодействия приложения с моделью и внешними инструментами.
- **stdio transport** — режим MCP, передающий протокольные сообщения через stdin/stdout. Произвольный текст в stdout может повредить обмен протоколом, поэтому журнал направляем в stderr.
- **Timeout (тайм-аут)** — максимальное время ожидания операции.
- **Validation (валидация)** — проверка типа и допустимого значения.
- **Fail fast (ранний отказ)** — принцип, при котором программа сразу сообщает о неправильной конфигурации.

## 3. Параметры конфигурации

| Переменная | По умолчанию | Диапазон | Назначение |
|---|---:|---:|---|
| WEB_TIMEOUT_SECONDS | 15 | 1–60 | Тайм-аут HTTP-запроса |
| WEB_SEARCH_MAX_RESULTS | 5 | 1–10 | Количество результатов |
| WEB_FETCH_MAX_PAGE_CHARS | 12000 | 1–100000 | Максимум символов страницы |
| WEB_FETCH_MAX_REDIRECTS | 3 | 0–10 | Максимум перенаправлений |
| WEB_FETCH_MAX_RESPONSE_BYTES | 1000000 | 1024–5000000 | Максимальный размер ответа в байтах |
| WEB_SEARCH_LOG_LEVEL | INFO | DEBUG, INFO, WARNING, ERROR, CRITICAL | Подробность журнала |

Диапазоны нужны, потому что конфигурация тоже является входными данными. Тайм-аут 0 секунд практически не даёт времени на запрос, а чрезмерный лимит ответа может привести к расходу памяти. Значения по умолчанию позволяют запускать сервер без обязательной настройки.

## 4. Код конфигурации: config.py

Замените содержимое src/web_search_mcp/config.py:

~~~python
"""Настройки MCP-сервера, читаемые из переменных окружения."""

import os

SERVER_NAME = "web-search-mcp"


def _env_int(name: str, default: int, minimum: int, maximum: int) -> int:
    """Читает целое число из окружения и проверяет допустимый диапазон."""
    raw_value = os.getenv(name)
    if raw_value is None or not raw_value.strip():
        return default

    try:
        value = int(raw_value)
    except ValueError as error:
        raise ValueError(f"{name} must be an integer.") from error

    if not minimum <= value <= maximum:
        raise ValueError(f"{name} must be between {minimum} and {maximum}.")

    return value


DEFAULT_TIMEOUT_SECONDS = _env_int("WEB_TIMEOUT_SECONDS", 15, 1, 60)
DEFAULT_MAX_SEARCH_RESULTS = _env_int("WEB_SEARCH_MAX_RESULTS", 5, 1, 10)
DEFAULT_MAX_PAGE_CHARS = _env_int("WEB_FETCH_MAX_PAGE_CHARS", 12_000, 1, 100_000)
MAX_REDIRECTS = _env_int("WEB_FETCH_MAX_REDIRECTS", 3, 0, 10)
MAX_RESPONSE_BYTES = _env_int("WEB_FETCH_MAX_RESPONSE_BYTES", 1_000_000, 1_024, 5_000_000)

LOG_LEVEL = os.getenv("WEB_SEARCH_LOG_LEVEL", "INFO").strip().upper()
_ALLOWED_LOG_LEVELS = {"DEBUG", "INFO", "WARNING", "ERROR", "CRITICAL"}
if LOG_LEVEL not in _ALLOWED_LOG_LEVELS:
    allowed = ", ".join(sorted(_ALLOWED_LOG_LEVELS))
    raise ValueError(f"WEB_SEARCH_LOG_LEVEL must be one of: {allowed}.")
~~~

### Разбор кода

import os подключает стандартный модуль os. os.getenv(name) читает переменную окружения. Если её нет, результатом будет None. Переменные окружения поступают в программу как строки, поэтому числовое значение нужно преобразовать.

Функция _env_int принимает имя настройки, значение по умолчанию и минимальную/максимальную границы. Аннотация -> int указывает ожидаемый тип результата. Аннотации помогают разработчикам и инструментам анализа, но не заменяют проверку значения во время выполнения.

**Конструкция is None** проверяет именно отсутствие значения. Условие raw_value is None or not raw_value.strip() означает: переменная отсутствует ИЛИ содержит только пробелы. strip() убирает пробелы по краям, or означает «или», not инвертирует логическое значение.

**Конструкция try / except** нужна, чтобы обработать ситуацию, когда int(raw_value) не может преобразовать строку в число. В этом случае Python возбуждает ValueError. Блок except перехватывает ошибку и позволяет выдать более понятное сообщение.

**Конструкция raise ... from error** — важное дополнение. raise возбуждает новое исключение, а from error сохраняет связь с первоначальной причиной. Это упрощает диагностику.

Проверка minimum <= value <= maximum — цепочка сравнений, эквивалентная minimum <= value and value <= maximum. Если число за пределами диапазона, программа отказывается запускаться с неверной настройкой. Числа 12_000 и 1_000_000 содержат подчёркивания только для удобства чтения: числовое значение не меняется.

В конце уровень журнала нормализуется с помощью strip().upper(). Значения info, INFO и строка с пробелами превращаются в INFO. Множество _ALLOWED_LOG_LEVELS хранит допустимые варианты. Если передать неизвестный уровень, конфигурация выдаст ошибку.

Почему это лучше, чем набор констант? Настройки можно менять без правки алгоритма, диапазоны проверяются централизованно, а разные модули используют одни значения. Конфигурация считывается при импорте модуля: изменение переменной после импорта не обновляет уже загруженное значение. Для применения новой настройки перезапустите процесс.

## 5. Логирование в server.py

Замените src/web_search_mcp/server.py:

~~~python
import logging
import sys

from mcp.server.fastmcp import FastMCP

from .config import (
    DEFAULT_MAX_PAGE_CHARS,
    DEFAULT_MAX_SEARCH_RESULTS,
    LOG_LEVEL,
    SERVER_NAME,
)
from .web_fetch import web_fetch
from .web_search import web_search

mcp = FastMCP(SERVER_NAME)


@mcp.tool()
def search_web(query: str, max_results: int = DEFAULT_MAX_SEARCH_RESULTS) -> dict:
    """Search the web and return page titles, URLs, and snippets."""
    return web_search(query=query, max_results=max_results)


@mcp.tool()
def fetch_web_page(url: str, max_chars: int = DEFAULT_MAX_PAGE_CHARS) -> dict:
    """Fetch a web page and return its title and readable text."""
    return web_fetch(url=url, max_chars=max_chars)


def configure_logging() -> None:
    """Send diagnostic logs to stderr so stdio remains available to MCP."""
    logging.basicConfig(
        level=LOG_LEVEL,
        stream=sys.stderr,
        format="%(asctime)s %(levelname)s %(name)s: %(message)s",
    )


def main() -> None:
    """Run the MCP server over standard input and output."""
    configure_logging()
    logging.getLogger(__name__).info("Starting MCP server: %s", SERVER_NAME)
    mcp.run(transport="stdio")


if __name__ == "__main__":
    main()
~~~

import logging подключает систему журналирования, а import sys предоставляет доступ к системным потокам. configure_logging() вызывает logging.basicConfig() и задаёт уровень, поток и формат. Значение stream=sys.stderr принципиально важно: MCP-транспорт stdio использует stdout для сообщений протокола.

Формат %(asctime)s %(levelname)s %(name)s: %(message)s включает время, уровень, имя модуля и сообщение. logging.getLogger(__name__) получает регистратор текущего модуля, а info() записывает сообщение уровня INFO. Маркер %s обозначает место для подстановки имени сервера.

Не используйте print() для отладки работающего MCP-сервера: произвольная строка в stdout может быть воспринята клиентом как повреждённое протокольное сообщение. Диагностические сообщения отправляем в stderr. Условие if __name__ == "__main__" запускает main() только при запуске файла как программы, а не при импорте.

## 6. Добавляем сообщения в Web Search

В src/web_search_mcp/web_search.py добавьте импорт logging и регистратор:

~~~python
import logging
from urllib.parse import urljoin

import httpx
from bs4 import BeautifulSoup

from .config import DEFAULT_MAX_SEARCH_RESULTS, DEFAULT_TIMEOUT_SECONDS

logger = logging.getLogger(__name__)
~~~

В обработчике сетевой ошибки используйте:

~~~python
except httpx.HTTPError as error:
    logger.warning("Search request failed (%s).", type(error).__name__)
    return {
        "ok": False,
        "query": query,
        "results": [],
        "error": f"Search request failed: {type(error).__name__}.",
    }
~~~

Перед возвратом успешного результата добавьте:

~~~python
logger.info("Search completed: %d result(s).", len(results))
return {"ok": True, "query": query.strip(), "results": results, "error": None}
~~~

logger.warning() записывает предупреждение, logger.info() — обычное событие. type(error).__name__ возвращает имя класса ошибки, например ConnectTimeout. len(results) считает результаты, а %d подставляет целое число.

Не записывайте в журнал полные пользовательские запросы, секреты, токены или весь текст веб-страницы без необходимости. Запрос может содержать внутреннюю или персональную информацию. Для базовой диагностики достаточно записать тип ошибки и количество результатов.

В Web Fetch полезно добавить аналогичные события: тайм-аут, HTTP-ошибка, неподдерживаемый тип содержимого и успешная загрузка с количеством символов. Это вынесено в практическое задание. Сохраняйте структуру результата функции: журнал и ответ инструмента — разные каналы.

## 7. Переменные окружения в PowerShell

Из корня проекта в PowerShell задайте параметры на текущий сеанс:

~~~powershell
$env:WEB_TIMEOUT_SECONDS = "20"
$env:WEB_SEARCH_MAX_RESULTS = "7"
$env:WEB_FETCH_MAX_PAGE_CHARS = "18000"
$env:WEB_FETCH_MAX_REDIRECTS = "3"
$env:WEB_FETCH_MAX_RESPONSE_BYTES = "1500000"
$env:WEB_SEARCH_LOG_LEVEL = "DEBUG"
~~~

Синтаксис $env:ИМЯ = "значение" устанавливает переменную для текущего процесса PowerShell и дочерних процессов, которые он запускает. Значения передаются строками — это нормально, потому что наша функция преобразует числа.

Проверить значение:

~~~powershell
$env:WEB_TIMEOUT_SECONDS
~~~

Ожидаемый вывод:

~~~text
20
~~~

Удалить переменную и вернуться к настройке по умолчанию:

~~~powershell
Remove-Item Env:WEB_TIMEOUT_SECONDS
~~~

Переменные такого сеанса не обязательно сохраняются после закрытия PowerShell. Это удобно для экспериментов.

## 8. Проверка конфигурации

Активируйте виртуальное окружение и задайте путь к исходникам:

~~~powershell
.\.venv\Scripts\Activate.ps1
$env:PYTHONPATH = "src"
~~~

Если виртуальное окружение имеет другое имя, используйте фактический путь. Проверьте настройки:

~~~powershell
python -c "from web_search_mcp.config import *; print(DEFAULT_TIMEOUT_SECONDS, DEFAULT_MAX_SEARCH_RESULTS, DEFAULT_MAX_PAGE_CHARS, MAX_REDIRECTS, MAX_RESPONSE_BYTES, LOG_LEVEL)"
~~~

Без заданных переменных ожидается:

~~~text
15 5 12000 3 1000000 INFO
~~~

Зададим настройки:

~~~powershell
$env:WEB_TIMEOUT_SECONDS = "20"
$env:WEB_SEARCH_MAX_RESULTS = "7"
python -c "from web_search_mcp.config import *; print(DEFAULT_TIMEOUT_SECONDS, DEFAULT_MAX_SEARCH_RESULTS)"
~~~

Ожидается:

~~~text
20 7
~~~

Каждый вызов python -c запускает отдельный процесс, поэтому конфигурация импортируется заново.

Проверим неверное значение:

~~~powershell
$env:WEB_TIMEOUT_SECONDS = "много"
python -c "from web_search_mcp.config import DEFAULT_TIMEOUT_SECONDS"
~~~

Ожидается ошибка, что WEB_TIMEOUT_SECONDS должно быть целым числом. Это ожидаемый ранний отказ. Верните настройку:

~~~powershell
$env:WEB_TIMEOUT_SECONDS = "15"
~~~

Проверим выход за диапазон:

~~~powershell
$env:WEB_SEARCH_MAX_RESULTS = "100"
python -c "from web_search_mcp.config import DEFAULT_MAX_SEARCH_RESULTS"
~~~

Программа должна сообщить о диапазоне от 1 до 10. После проверки верните корректное значение или удалите переменную.

## 9. Настройки LM Studio

Если MCP-сервер запускает LM Studio, он не обязательно наследует переменные, заданные в отдельном окне PowerShell. Для настройки через LM Studio добавляйте значения в поле env файла mcp.json. Пример:

~~~json
{
  "mcpServers": {
    "cherkashin-web-search": {
      "command": "C:\\ПУТЬ_К_ПРОЕКТУ\\.venv\\Scripts\\python.exe",
      "args": ["-m", "web_search_mcp.server"],
      "env": {
        "PYTHONPATH": "C:\\ПУТЬ_К_ПРОЕКТУ\\src",
        "WEB_TIMEOUT_SECONDS": "20",
        "WEB_SEARCH_MAX_RESULTS": "7",
        "WEB_FETCH_MAX_PAGE_CHARS": "18000",
        "WEB_SEARCH_LOG_LEVEL": "INFO"
      }
    }
  }
}
~~~

Это пример: замените путь на фактический. JSON требует двойных кавычек и корректных запятых. Обратная косая черта в JSON экранируется, поэтому Windows-пути записываются с двойными обратными косыми чертами. После изменения конфигурации перезапустите MCP-сервер или переподключите его в LM Studio.

Из корня проекта запустите:

~~~powershell

~~~

Флаг -q сокращает вывод pytest. Оценивайте фактический результат команды, не предполагайте заранее, что тесты пройдут.

Проверить импорт сервера и функцию настройки журнала можно отдельно:

~~~powershell
python -c "from web_search_mcp.server import configure_logging; configure_logging(); print('Импорт сервера и настройка журнала выполнены')"
~~~

Здесь print() используется в отдельном диагностическом процессе, где MCP-транспорт не запущен. В работающем сервере произвольный вывод в stdout недопустим.

Успешный импорт не подтверждает доступность поисковика, правильность HTML-разметки всех сайтов или фактический вызов инструментов из LM Studio. Автоматические тесты, реальные сетевые проверки и интеграционный тест — разные виды проверки.

## 11. Частые ошибки

- **WEB_TIMEOUT_SECONDS must be an integer.** Значение нельзя преобразовать в целое число. Укажите, например, 20.
- **WEB_SEARCH_MAX_RESULTS must be between 1 and 10.** Значение за пределами разрешённого диапазона.
- **LM Studio не применяет настройки.** Проверьте поле env и перезапустите MCP-сервер.
- **Журнал не виден в обычном выводе.** Он направлен в stderr; приложение может показывать этот поток отдельно.
- **В ответе инструмента нет сообщения журнала.** Это правильно: журнал и результат инструмента — разные каналы.
- **Изменение переменной не влияет на уже работающий процесс.** Конфигурация была импортирована раньше; перезапустите процесс.
- **Не находится пакет web_search_mcp.** Запустите команду из корня проекта и задайте PYTHONPATH равным src.
- **В MCP попадает лишний текст.** Уберите print() из серверного stdout и используйте журналирование в stderr.

## 15. Итог урока

Мы вынесли настройки в переменные окружения, добавили проверки типа и диапазона, настроили журналирование стандартным модулем Python и направили диагностические сообщения в stderr.

Запомните:
- конфигурацию нужно проверять, а не принимать вслепую;
- значения по умолчанию позволяют запускаться без обязательной настройки;
- ошибку конфигурации лучше обнаружить при старте;
- журнал должен помогать диагностике и не раскрывать лишние данные;
- при MCP stdio нельзя использовать stdout для произвольных сообщений;
- успешный автоматический тест не равен фактической проверке в LM Studio.

**Критерии готовности:** параметры читаются из окружения, неверные значения отклоняются, журнал направлен в stderr, поиск создаёт диагностические записи, тесты запущены и их фактический результат зафиксирован. Интеграцию с LM Studio следует проверить отдельно.
