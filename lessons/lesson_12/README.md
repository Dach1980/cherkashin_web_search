# Урок № 12. Подключаем MCP-сервер к LM Studio и запускаем без VS Code

## 1. Цель урока

В уроке № 10 мы объединили функции поиска и загрузки страниц в MCP-сервер. В уроке № 11 добавили защитные проверки и автоматические тесты. Теперь подключим сервер к LM Studio, проверим обнаружение инструментов, запустим поиск и загрузку страницы, а затем настроим автоматический запуск сервера самой LM Studio.

Ключевой результат: после настройки не нужно каждый раз открывать VS Code и вручную вводить команду запуска. LM Studio сможет запускать Python-процесс MCP-сервера при подключении к нему. При этом Python и виртуальное окружение проекта остаются установленными на компьютере. Самостоятельный EXE-файл — отдельная задача, не выполняемая в этом уроке.

В уроке мы:
1. проверим структуру проекта и виртуальное окружение;
2. запустим сервер вручную и проверим импорт;
3. настроим файл `mcp.json` для LM Studio;
4. проверим, что LM Studio видит инструменты `search_web` и `fetch_web_page`;
5. проведём практическую цепочку «поиск → загрузка страницы → ответ»;
6. разберём типовые ошибки и диагностику;
7. научимся повторно запускать тесты после изменения кода.

## 2. Иностранные термины и определения

**Integration (интеграция)** — соединение нескольких программных компонентов так, чтобы они совместно выполняли задачу. В нашем случае LM Studio выступает MCP-клиентом, а Python-сервер предоставляет инструменты.

**Host (хост)** — приложение, в котором работает модель и которое организует доступ к дополнительным инструментам. В нашем курсе это LM Studio.

**MCP client (MCP-клиент)** — компонент, который подключается к MCP-серверу, получает описание доступных инструментов и отправляет запросы на их выполнение.

**MCP server (MCP-сервер)** — программа, которая предоставляет инструменты по протоколу MCP. В нашем проекте это модуль `web_search_mcp.server`.

**Tool discovery (обнаружение инструментов)** — процесс, при котором клиент узнаёт, какие инструменты предоставляет сервер, какие аргументы они принимают и какие результаты возвращают.

**Transport (транспорт)** — способ передачи сообщений между клиентом и сервером. В нашем проекте используется `stdio`: стандартный ввод и стандартный вывод запущенного процесса.

**stdio (standard input/output — стандартный ввод/вывод)** — каналы процесса, обычно обозначаемые stdin и stdout. MCP-сообщения передаются по этим каналам. Нельзя выводить произвольные диагностические сообщения в stdout: они могут нарушить протокол. Для отладки используйте stderr или журналирование, согласованное с используемым SDK.

**Process (процесс)** — выполняющийся экземпляр программы с собственным состоянием и ресурсами. LM Studio может запустить отдельный процесс Python для локального MCP-сервера.

**Working directory (рабочая директория)** — каталог, относительно которого программа разрешает относительные пути. Запуск из разных каталогов может приводить к разным результатам, поэтому мы используем абсолютные пути.

**Virtual environment / venv (виртуальное окружение)** — отдельное окружение Python для проекта, где устанавливаются его зависимости. Оно помогает не смешивать библиотеки разных проектов.

**Interpreter (интерпретатор)** — программа, которая выполняет Python-код. В конфигурации нужно указать тот интерпретатор, в котором установлены зависимости проекта.

**JSON (JavaScript Object Notation)** — текстовый формат структурированных данных: объектов, массивов, строк, чисел, логических значений и null. Файл `mcp.json` содержит конфигурацию MCP-серверов.

**Absolute path (абсолютный путь)** — полный путь к файлу или каталогу, например `C:\Projects\cherkashin_web_search\.venv\Scripts\python.exe`. Он не зависит от текущей рабочей директории.

**Smoke test (дымовой тест)** — короткая первичная проверка, которая подтверждает, что компонент хотя бы запускается и выполняет базовую операцию. Успешный импорт сервера — дымовой тест, но не полная проверка взаимодействия с LM Studio.

**Tool calling (вызов инструмента)** — ситуация, когда модель выбирает зарегистрированный инструмент и формирует аргументы для его запуска. Возможность вызова зависит от настроек приложения и способностей конкретной модели.

**Context window (контекстное окно)** — объём текста и данных, который модель может учитывать в одном запросе. Результаты поиска и содержимое страниц расходуют контекст, поэтому не следует передавать модели большие документы без необходимости.

## 3. Как устроена итоговая система

~~~text
Пользователь
    |
    v
LM Studio + локальная языковая модель
    |
    | MCP client
    v
Python MCP server (stdio)
    |
    +--> search_web(query, max_results)
    |         |
    |         v
    |      web_search.py --> поисковая HTML-страница
    |
    +--> fetch_web_page(url, max_chars)
              |
              v
           web_fetch.py --> выбранная веб-страница
~~~

Разделение обязанностей:
- **LM Studio** предоставляет интерфейс общения с моделью и управляет подключением к MCP-серверу.
- **Модель** решает, когда ей нужен инструмент, и формирует аргументы.
- **MCP-сервер** описывает доступные инструменты и принимает вызовы.
- **web_search.py** выполняет поиск и возвращает список результатов.
- **web_fetch.py** загружает выбранную страницу, извлекает текст и применяет защитные ограничения.

Сервер не гарантирует, что модель всегда выберет правильный инструмент. Мы предоставляем понятные описания и предсказуемые ответы, а модель использует их в рамках своего поведения.

## 4. Проверяем проект перед подключением

Откройте PowerShell и перейдите в каталог проекта. Замените путь примером на фактический путь к вашему репозиторию:

~~~powershell
cd C:\Projects\cherkashin_web_search
Get-ChildItem
~~~

В корне проекта должны быть видны как минимум `README.md`, `requirements.txt`, `src`, `tests` и `lessons`.

Активируем виртуальное окружение:

~~~powershell
.\.venv\Scripts\Activate.ps1
~~~

Если папки `.venv` нет, создайте её и установите зависимости:

~~~powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
~~~

Разбор:
- `python -m venv .venv` запускает модуль стандартной библиотеки `venv` и создаёт окружение в папке `.venv`.
- `python -m pip` запускает менеджер пакетов через текущий интерпретатор. Так меньше риск установить библиотеку не в то окружение.
- `-r requirements.txt` означает прочитать список зависимостей из файла.
- `Activate.ps1` активирует окружение в текущей сессии PowerShell.

Проверим интерпретатор:

~~~powershell
python --version
python -c "import sys; print(sys.executable)"
~~~

Вторая команда выводит путь к Python. Убедитесь, что это интерпретатор из виртуального окружения проекта, а не другой Python, установленный в системе.

## 5. Запускаем автоматические тесты

До подключения к LM Studio проверим функции и защитные ограничения:

~~~powershell
$env:PYTHONPATH = "src"
python -m pytest -q
~~~

Первая команда задаёт переменную окружения `PYTHONPATH` для текущей сессии PowerShell. Значение `src` указывает Python, где искать пакет `web_search_mcp`. Вторая команда запускает тесты.

Если тесты не прошли, сначала разберите ошибку. Подключение MCP не исправит проблемы в поиске или загрузке страниц. Если тесты проходят, продолжайте настройку.

## 6. Проверяем импорт MCP-сервера

Выполните:

~~~powershell
$env:PYTHONPATH = "src"
python -c "from web_search_mcp.server import mcp; print('Импорт MCP-сервера выполнен')"
~~~

Команда `python -c` выполняет Python-код, переданный строкой. Мы импортируем объект `mcp` из модуля сервера. Если импорт успешен, зависимости установлены и модуль доступен.

Это только дымовой тест. Он не доказывает, что LM Studio подключилась, обнаружила инструменты или может вызвать их. Сообщение `print()` здесь безопасно, потому что команда не запускает транспорт MCP. В серверном процессе нельзя печатать произвольные сообщения в stdout.

## 7. Ручной запуск MCP-сервера

В отдельном окне PowerShell выполните:

~~~powershell
$env:PYTHONPATH = "src"
python -m web_search_mcp.server
~~~

Команда запускает модуль как программу. При нормальной работе сервер может выглядеть как «ничего не происходит»: это ожидаемо для stdio-транспорта. Он ждёт сообщения MCP по стандартному вводу, а не открывает обычную веб-страницу в браузере.

Не вводите в это окно произвольный текст и не добавляйте `print()` в серверный код для диагностики: stdout является каналом протокола. Для завершения ручного теста обычно можно нажать Ctrl+C.

Если процесс немедленно завершился с ошибкой, сохраните полный traceback. Проверьте путь к интерпретатору, наличие зависимостей и корректность импорта. Не исправляйте ошибку случайными изменениями сразу в нескольких файлах.

## 8. Настраиваем LM Studio через mcp.json

LM Studio поддерживает подключение локальных MCP-серверов через файл конфигурации `mcp.json`. В документации LM Studio указано, что серверы можно добавлять через интерфейс приложения: открыть вкладку Program, затем Install → Edit mcp.json. Названия и расположение элементов могут меняться между версиями. См. [официальную документацию LM Studio по MCP](https://lmstudio.ai/docs/app/mcp).

Откройте LM Studio и найдите редактор `mcp.json`. Если файл уже содержит другие серверы, не удаляйте их. Добавьте наш сервер внутрь существующего объекта `mcpServers`, сохранив корректный JSON.

Пример конфигурации:

~~~json
{
  "mcpServers": {
    "cherkashin-web-search": {
      "command": "C:\\Projects\\cherkashin_web_search\\.venv\\Scripts\\python.exe",
      "args": [
        "-m",
        "web_search_mcp.server"
      ],
      "env": {
        "PYTHONPATH": "C:\\Projects\\cherkashin_web_search\\src"
      }
    }
  }
}
~~~

Это пример для Windows. Обязательно замените путь `C:\Projects\cherkashin_web_search` на фактический каталог вашего проекта. В JSON обратная косая черта в пути экранируется дополнительной обратной косой чертой. Например, путь Windows записывается в JSON как `C:\Projects\cherkashin_web_search\.venv\Scripts\python.exe`.

В репозитории также лежит шаблон `examples/lmstudio.mcp.json`. В нём используется заполнитель пути, поэтому его необходимо заменить до подключения.

### Разбор полей конфигурации

**`mcpServers`** — объект, в котором перечисляются MCP-серверы. Имя `cherkashin-web-search` — локальное имя подключения; его можно изменить.

**`command`** — команда, которую LM Studio запускает. Мы указываем абсолютный путь к Python внутри виртуального окружения. Это важно: системный Python может не иметь установленных зависимостей проекта.

**`args`** — список аргументов команды. `-m` означает, что Python должен найти модуль и запустить его как программу. Следующий аргумент — `web_search_mcp.server`, путь к модулю в Python-нотации через точки.

**`env`** — переменные окружения процесса. Мы задаём `PYTHONPATH` абсолютным путём к каталогу `src`, чтобы импорт пакета не зависел от рабочей директории, из которой LM Studio запускает процесс.

В JSON строки заключаются в двойные кавычки. Элементы списка разделяются запятыми. После последнего элемента запятая не ставится. Комментарии вида `// комментарий` в стандартном JSON не разрешены.

### Частая ошибка: неверный путь

Если в поле `command` указан несуществующий путь, LM Studio не сможет запустить Python. Если `PYTHONPATH` указывает не на `src`, импорт `web_search_mcp` может завершиться ошибкой.

Если у вас уже есть объект `mcpServers`, вставляйте только запись `"cherkashin-web-search": { ... }` внутрь него, не создавая второй объект верхнего уровня `mcpServers`. Сохраняйте существующие настройки других серверов.

## 9. Почему запуск без VS Code работает

LM Studio запускает указанную команду самостоятельно. Поэтому не требуется оставлять открытым редактор кода или отдельное окно PowerShell. Однако Python-процесс всё равно работает в операционной системе, а виртуальное окружение и файлы проекта должны оставаться на диске.

Это не означает, что программа уже упакована в самостоятельный EXE. В текущем варианте запуск зависит от:
- Python в виртуальном окружении;
- установленных библиотек из `requirements.txt`;
- доступности исходников проекта;
- корректного абсолютного пути в `mcp.json`.

Если переместить проект в другую папку, путь в конфигурации тоже нужно обновить.

## 10. Перезагружаем подключение и проверяем инструменты

После сохранения конфигурации выполните действие, предусмотренное вашей версией LM Studio: перезагрузите список MCP-серверов или перезапустите приложение. Откройте интерфейс управления MCP-инструментами и найдите `cherkashin-web-search`.

Ожидаемый результат:
- сервер отображается в списке;
- сервер запускается без ошибки;
- обнаруживаются инструменты `search_web` и `fetch_web_page`;
- в описаниях видны аргументы и их типы.

Если сервер отображается, но инструменты не видны, проверьте:
1. что в `server.py` декоратор `@mcp.tool()` стоит над каждой функцией;
2. что импорт `web_search` и `web_fetch` не вызывает исключение;
3. что конфигурация указывает на правильный Python;
4. что тесты проходят.

Не запускайте один и тот же stdio-сервер вручную и одновременно через LM Studio, если вы не тестируете два независимых процесса намеренно. Для обычной проверки достаточно одного экземпляра, который запускает клиент.

## 11. Практическая проверка поиска

В чате LM Studio загрузите модель, поддерживающую использование инструментов, и отправьте запрос:

~~~text
Найди в интернете официальный сайт Python и верни название страницы и URL. Используй инструмент поиска, если он доступен.
~~~

Модель может сформировать вызов `search_web`. Инструмент обращается к поисковому провайдеру и возвращает список результатов. Затем модель анализирует полученный список.

Если модель ответила из собственной памяти и не вызвала инструмент, это ещё не доказывает, что MCP-сервер сломан. Уточните запрос: попросите явно использовать инструмент и вывести результат вызова. Убедитесь, что инструменты разрешены в интерфейсе и модель умеет ими пользоваться.

Результат зависит от внешнего поискового провайдера: доступность, HTML-разметка и правила сайта могут меняться. Успешный тест сегодня не гарантирует неизменную работу провайдера в будущем.

## 12. Практическая проверка загрузки страницы

Попросите модель загрузить известную публичную страницу:

~~~text
Используй fetch_web_page для загрузки https://example.com. Кратко перескажи содержимое на основании текста, который вернул инструмент. Если инструмент вернёт ошибку, сообщи об ошибке, а не выдумывай содержимое страницы.
~~~

Ожидаемая последовательность:
1. модель вызывает `fetch_web_page` с URL;
2. сервер проверяет URL и применяет защитные ограничения;
3. функция получает HTTP-ответ и извлекает текст;
4. инструмент возвращает результат;
5. модель формирует ответ на основе возвращённого содержимого.

Если инструмент вернул `ok: false`, это не обязательно ошибка MCP. Возможно, отказала проверка URL, сайт недоступен, запрос превысил лимит или сервер получил сетевую ошибку. Прочитайте поле `error` и диагностируйте конкретную причину.

## 13. Проверяем цепочку «поиск → загрузка → ответ»

Используйте запрос:

~~~text
Найди официальную документацию Python по теме виртуальных окружений. Сначала вызови search_web, выбери подходящий результат, затем вызови fetch_web_page для его URL. Сформулируй краткое резюме и отдельно укажи, какие факты получены из загруженной страницы.
~~~

При успешной интеграции модель должна:
1. вызвать поиск;
2. получить список результатов;
3. выбрать URL;
4. вызвать загрузку;
5. получить текст страницы;
6. подготовить ответ.

Если цепочка обрывается после поиска, проверьте, что модель видит второй инструмент и понимает его описание. Если загрузка сработала, но ответ не содержит фактов из страницы, проверьте объём возвращаемого текста и контекстное окно модели.

Не оценивайте работу только по внешнему виду финального ответа. Изучите историю вызовов инструментов и их результаты, если эта информация доступна в вашей версии LM Studio.

## 14. Типичные ошибки и способы исправления

### Ошибка 1. LM Studio не находит Python

**Причина:** в поле `command` указан несуществующий или относительный путь.

**Решение:** скопируйте полный путь командой:

~~~powershell
python -c "import sys; print(sys.executable)"
~~~

Используйте полученный путь в `command`.

### Ошибка 2. No module named web_search_mcp

**Причина:** процесс не видит каталог `src`.

**Решение:** проверьте `PYTHONPATH` в `env`. Он должен указывать на абсолютный путь к каталогу `src` вашего проекта, а не к самому пакету `web_search_mcp`.

### Ошибка 3. No module named mcp

**Причина:** выбран другой Python или зависимости не установлены в виртуальное окружение.

**Решение:**

~~~powershell
.\.venv\Scripts\python.exe -m pip show mcp
~~~

Если пакет не найден, установите зависимости:

~~~powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
~~~

### Ошибка 4. Конфигурация JSON не принимается

**Причина:** лишняя запятая, кавычка, неверный путь или повторный объект `mcpServers`.

**Решение:** проверьте структуру скобок и запятых. Если файл уже содержит `mcpServers`, добавьте запись внутрь существующего объекта. Не удаляйте другие серверы.

### Ошибка 5. Сервер сразу завершается

**Причина:** исключение при импорте, неверная команда, недостающая библиотека или ошибка в коде.

**Решение:** запустите ту же команду вручную из PowerShell с тем же интерпретатором. Полный traceback обычно показывает, какой модуль или строка вызвали сбой.

### Ошибка 6. Инструменты видны, но поиск ничего не возвращает

**Причина:** сетевой сбой, блокировка поискового провайдера, изменение HTML или пустая выдача.

**Решение:** проверьте результат инструмента и поле ошибки. Затем запустите тесты поиска. Не путайте успешное подключение MCP с успешностью внешнего поискового сервиса.

### Ошибка 7. Инструмент работает в тестах, но не вызывается моделью

**Причина:** инструменты не разрешены в чате, модель не использует tool calling или запрос допускает ответ из памяти.

**Решение:** проверьте доступность инструментов в интерфейсе и попросите модель явно вызвать конкретный инструмент. Если модель не поддерживает инструментальные вызовы, исправный сервер не добавит ей эту способность автоматически.

### Ошибка 8. После переноса проекта всё перестало работать

**Причина:** абсолютные пути в `mcp.json` указывают на старое местоположение.

**Решение:** обновите `command` и `PYTHONPATH`. Затем повторите импорт и тесты.

## 15. Проверка после изменения кода

Каждый раз, когда меняете сервер, функции поиска или загрузки, используйте один и тот же порядок:

~~~powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
$env:PYTHONPATH = "src"
python -m pytest -q
python -c "from web_search_mcp.server import mcp; print('Импорт MCP-сервера выполнен')"
~~~

Первая команда синхронизирует зависимости с файлом проекта. Вторая задаёт путь для поиска пакета в текущем терминале. Третья запускает автоматические тесты. Четвёртая проверяет импорт.

После этого отдельно проверяйте MCP в LM Studio. Автоматические тесты проверяют код, импорт проверяет доступность модуля, а реальный вызов инструмента проверяет интеграцию — это три разных уровня.

Мы прошли путь от отдельных Python-функций до MCP-сервера, который предоставляет модели два инструмента: поиск в интернете и загрузку страницы. - LM Studio видит сервер;
- доступны инструменты `search_web` и `fetch_web_page`;
- поиск возвращает структурированные результаты;
- загрузка возвращает читаемый текст;
- модель может выполнить цепочку поиска и загрузки;
