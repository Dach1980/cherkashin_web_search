# Урок № 15. Углублённое тестирование MCP-сервера

## 1. Зачем нужен этот урок

В предыдущих уроках мы создали две обычные Python-функции — `web_search()` и `web_fetch()`, объединили их в MCP-сервер и описали структуру ответов с помощью `TypedDict`. Теперь нужно убедиться, что программа ведёт себя правильно не только в удачном сценарии, но и при ошибках.

Недостаточно один раз запустить программу и увидеть, что она не завершилась с исключением. Поисковая система может вернуть ошибку HTTP, соединение может прерваться, сайт может отдать PDF вместо HTML, перенаправить запрос на запрещённый адрес или прислать слишком большой документ. Сервер должен обработать такие ситуации предсказуемо.

В этом уроке мы расширяем автоматические тесты проекта. Мы проверим:
- разбор поисковой выдачи и нормализацию запроса;
- обработку сетевых ошибок и ошибочных HTTP-статусов;
- проверку URL и запрет обращения к локальным адресам;
- извлечение текста HTML и удаление служебных элементов;
- ограничение длины извлечённого текста и размера ответа;
- единый формат успешных ответов и ошибок;
- различие между автоматическим тестированием функций, тестированием MCP-протокола и ручной проверкой в LM Studio.

**Главная мысль:** хороший тест проверяет наблюдаемое поведение программы, а не просто то, что строка кода выполнилась.

## 2. Словарь иностранных терминов

- **Test (тест)** — автоматическая или ручная проверка того, что программа ведёт себя ожидаемым образом.
- **Testing (тестирование)** — процесс проверки программы на правильность, устойчивость и соответствие требованиям.
- **Unit test (модульный тест)** — проверка небольшого изолированного элемента, например одной функции.
- **Integration test (интеграционный тест)** — проверка совместной работы нескольких частей системы.
- **End-to-end test, E2E (сквозной тест)** — проверка полного пользовательского пути от начального действия до конечного результата.
- **Regression test (регрессионный тест)** — тест, который повторно проверяет уже исправленную ситуацию, чтобы прежняя ошибка не появилась снова.
- **Assertion (утверждение)** — проверка ожидаемого условия. В pytest обычно используется оператор `assert`.
- **Fixture (фикстура)** — подготовленные данные или состояние, которое тест использует для проверки.
- **Mock (мок, имитация)** — подменённый объект или функция, имитирующие внешнюю зависимость, например интернет-запрос.
- **Monkeypatch (временная подмена)** — механизм pytest, позволяющий на время теста заменить функцию, атрибут или переменную.
- **Mocking (мокирование)** — создание таких подмен для изоляции проверяемого кода.
- **Isolation (изоляция)** — принцип, при котором тест не зависит от реального интернета, чужого сервера или порядка запуска других тестов.
- **Deterministic test (детерминированный тест)** — тест, который при одинаковых условиях даёт одинаковый результат.
- **Test coverage (покрытие тестами)** — доля кода или сценариев, охваченных тестами. Высокое покрытие не гарантирует отсутствие ошибок.
- **Edge case (граничный случай)** — ситуация на границе допустимых значений: пустая строка, максимальный размер, ноль, неправильный тип.
- **Regression (регрессия)** — повторное появление ранее устранённой ошибки после изменения кода.
- **HTTP status code (код состояния HTTP)** — число, которым веб-сервер сообщает результат запроса, например 200 или 503.
- **Protocol (протокол)** — правила обмена сообщениями между программами.
- **MCP client (клиент MCP)** — приложение, которое подключается к MCP-серверу и вызывает предоставленные инструменты; в нашем проекте эту роль может выполнять LM Studio.
- **Schema (схема)** — описание структуры данных или аргументов инструмента.
- **Network boundary (сетевая граница доверия)** — место, где программа взаимодействует с внешней сетью и должна считать полученные данные недоверенными.

## 3. Какие уровни тестирования существуют

### 3.1. Модульные тесты

Модульный тест проверяет одну небольшую часть программы. Например, передаём `web_search()` готовую имитацию HTML-ответа и проверяем, что из него извлечены заголовок, ссылка и описание.

Преимущество: тест быстро выполняется и помогает точно локализовать ошибку. Если проверка парсинга не прошла, мы знаем, что проблема находится в соответствующей функции или её ожиданиях, а не в LM Studio.

### 3.2. Интеграционные тесты

Интеграционный тест проверяет взаимодействие компонентов. Для нашего проекта это может быть цепочка:

`MCP-клиент → MCP-сервер → search_web → web_search → обработка результата → ответ клиенту`.

Тесты Python-функций не доказывают, что MCP-клиент смог запустить сервер и вызвать инструмент по протоколу. Для такого вывода нужна отдельная проверка MCP-уровня.

### 3.3. Сквозная проверка

Сквозная проверка проходит через реальное приложение. В нашем случае мы подключаем сервер к LM Studio, убеждаемся, что оба инструмента обнаруживаются, просим модель выполнить поиск и затем загрузить одну из страниц.

Это отдельный этап: автоматические тесты с подменённой сетью **не доказывают** доступность реальных поисковых сайтов и успешное подключение к LM Studio.

## 4. Как устроен тест pytest

Пример:

~~~python
def test_rejects_empty_query_without_network():
    result = search_module.web_search("   ")
    assert result["ok"] is False
    assert result["results"] == []
~~~

Разбор:
1. Имя функции начинается с `test_`. По умолчанию pytest ищет функции с таким префиксом в файлах `test_*.py` или `*_test.py`.
2. В функцию передаётся строка из пробелов. Это граничный случай: строка существует, но после удаления пробелов не содержит поискового запроса.
3. Функция возвращает словарь, который сохраняется в переменную `result`.
4. `assert` проверяет ожидаемые свойства результата.
5. Если условие ложно, pytest сообщает, какая проверка не прошла.

### Новый оператор: `assert`

`assert выражение` проверяет, что выражение истинно. Если оно ложно, Python возбуждает `AssertionError`. В тестах это удобный способ описать ожидаемое поведение обычными словами кода.

Преимущества:
- кратко и читаемо;
- pytest показывает значения, участвовавшие в неудачной проверке;
- не нужно вручную писать сообщения для каждого сравнения.

Важно: `assert` предназначен прежде всего для тестов и внутренних предположений. Не используйте его вместо проверки пользовательских данных в рабочем коде: Python может отключать assert при специальном режиме запуска.

## 5. Почему мы подменяем сеть

Если тест обращается к реальному сайту, его результат зависит от интернет-соединения, доступности сайта, защиты от роботов, DNS и изменений HTML. В таком тесте трудно понять, что сломалось: наша программа или внешний сервис.

Вместо реального HTTP-ответа тест передаёт заранее подготовленный ответ. Так проверяется наша логика обработки данных, а не состояние интернета.

Пример подмены:

~~~python
monkeypatch.setattr(
    search_module.httpx,
    "get",
    lambda *args, **kwargs: response,
)
~~~

Здесь:
- `monkeypatch.setattr(...)` временно заменяет атрибут;
- `search_module.httpx.get` — функция, которую вызывает модуль поиска;
- `lambda *args, **kwargs: response` — небольшая функция, возвращающая заранее созданный объект `response`;
- `*args` собирает дополнительные позиционные аргументы в кортеж;
- `**kwargs` собирает именованные аргументы в словарь;
- имена `args` и `kwargs` — общепринятые сокращения от arguments и keyword arguments.

**Почему используются `*` и `**`?** Тестовая функция не обязана повторять все параметры `httpx.get()`. Она принимает любые переданные аргументы, чтобы не зависеть от их количества, и возвращает подготовленный ответ.

### Новая конструкция: `lambda`

`lambda` создаёт небольшую анонимную функцию. В тестах она удобна для простой подмены, когда достаточно вернуть одно значение.

Преимущество — короткая запись. Ограничение — в `lambda` можно написать только одно выражение. Если подмена должна вести журнал вызовов, выполнять несколько шагов или выбрасывать исключение по условию, лучше использовать обычный `def`.

## 6. Разбор тестов поиска

В `tests/test_web_search.py` проверяются разные сценарии.

### Сценарий A. Пустой запрос

Ожидаем, что `web_search("   ")` вернёт `ok = False` и пустой список результатов, не вызывая сеть.

Почему это важно? Пустой запрос не должен расходовать время и создавать бессмысленный HTTP-запрос.

### Сценарий B. Корректная выдача

Тест создаёт HTML с элементами, соответствующими селекторам поиска. Затем подменяет HTTP-функцию и проверяет:
- `ok` равно `True`;
- количество результатов соответствует лимиту;
- заголовок извлечён;
- ссылка не потеряна;
- описание извлечено правильно.

### Сценарий C. Ошибка соединения

Подмена возбуждает исключение `httpx.ConnectError`. Функция поиска должна преобразовать сетевую проблему в предусмотренный контракт ответа, а не аварийно завершить весь MCP-сервер.

### Сценарий D. Ошибка HTTP

Сайт может ответить, например, кодом 503 — «сервис временно недоступен». Тест проверяет, что вызов `raise_for_status()` приводит к обработанному результату ошибки.

**Обратите внимание:** мы не проверяем, что поисковый сайт действительно доступен. Мы проверяем, что наша программа корректно обрабатывает заданные условия.

## 7. Разбор тестов загрузчика страницы

В `tests/test_web_fetch.py` тесты проверяют более широкий набор границ безопасности и качества данных.

### 7.1. Запрет локального адреса

Адрес `http://127.0.0.1/secret` указывает на локальный компьютер, а не на публичный сайт. Загрузчик должен отклонить его до выполнения HTTP-запроса.

Это важно, потому что инструментом может пользоваться языковая модель, а содержимое URL может прийти извне. Без ограничений сервер можно было бы попытаться использовать для обращения к локальным сервисам.

### 7.2. Только HTTP и HTTPS

URL схемы `file://` не является обычной публичной веб-страницей. Тест убеждается, что он отклоняется.

### 7.3. Перенаправление на запрещённый адрес

Обычный публичный URL может вернуть HTTP-перенаправление на другой адрес. Поэтому проверять нужно не только начальный URL: каждый следующий адрес также проходит валидацию. Регрессионный тест гарантирует, что перенаправление на loopback-адрес не приведёт к новому запросу.

### 7.4. Ограничение размера ответа

Сервер не должен без ограничений загружать большие документы в память. Тест имитирует слишком большой фрагмент и проверяет, что загрузчик возвращает ошибку ограничения размера.

### 7.5. Ограничение длины текста

Ограничение количества символов извлечённого текста и ограничение размера загруженного тела — **разные ограничения**:
- байтовый лимит ограничивает объём данных, получаемых по сети;
- лимит символов ограничивает объём текста, передаваемого дальше модели.

Оба нужны. Небольшой HTML может содержать много служебной разметки, а большой документ может перегрузить память ещё до извлечения текста.

### 7.6. Тайм-аут и ошибки соединения

Внешний сайт может не отвечать. Тест подменяет HTTP-клиент и заставляет его выдать исключение. Мы проверяем, что функция возвращает понятный структурированный результат, а не раскрывает пользователю внутренние подробности исключения.

## 8. Контракты ответа и регрессионные проверки

В уроке 14 мы создали `TypedDict` для `SearchResponse`, `SearchResult` и `FetchResponse`. Но аннотации типов сами по себе не заставляют Python проверять фактический словарь при каждом вызове.

Поэтому тесты контрактов проверяют, что успешный и неуспешный ответы содержат одинаковый набор ключей. Например, у поиска всегда есть:
- `ok` — успех или ошибка;
- `query` — исходный поисковый запрос;
- `results` — список результатов;
- `error` — текст ошибки или `None`.

Стабильный формат облегчает работу MCP-клиента: ему не приходится угадывать, будет ли поле отсутствовать при ошибке.

Тест контракта не заменяет проверку всех типов значений и не является полноценным валидатором схемы. Он фиксирует важные договорённости проекта и защищает от случайных изменений.

## 9. Как запустить тесты в Windows PowerShell

Открой терминал VS Code в папке проекта.

Если виртуальное окружение уже создано:

~~~powershell
.\.venv\Scripts\Activate.ps1
$env:PYTHONPATH = "src"
python -m pytest -q
~~~

Если окружение ещё не создано, сначала выполни:

~~~powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
$env:PYTHONPATH = "src"
python -m pytest -q
~~~

### Что означают команды

- `python -m venv .venv` создаёт виртуальное окружение.
- `Activate.ps1` активирует его в текущем терминале PowerShell.
- `python -m pip install -r requirements.txt` устанавливает перечисленные зависимости.
- `$env:PYTHONPATH = "src"` сообщает Python, где искать исходный пакет проекта. Переменная действует в текущем окне PowerShell.
- `python -m pytest -q` запускает pytest через текущий интерпретатор. Ключ `-q` означает quiet — сокращённый вывод.

### Как читать результат

Если все тесты прошли, pytest завершится с кодом 0 и покажет число прошедших проверок. Если тест упал, внимательно прочитай имя теста, строку `assert` и фактическое значение.

Если PowerShell сообщает, что выполнение сценариев запрещено, это ограничение политики запуска скриптов, а не ошибка Python-теста. Не меняй системную политику вслепую: можно запустить Python из активированного окружения через явный путь или настроить разрешённый способ активации для своего компьютера.

Если появляется `ModuleNotFoundError: No module named 'web_search_mcp'`, проверь, что терминал открыт в корне репозитория и задано `$env:PYTHONPATH = "src"`.

## 10. Почему мок-тесты не заменяют проверку MCP

Тесты функций доказывают, что поиск и загрузчик обрабатывают подготовленные входные данные правильно. Они не доказывают автоматически, что:
- сервер стартует в режиме `stdio`;
- MCP-клиент видит инструменты `search_web` и `fetch_web_page`;
- схема аргументов передаётся клиенту в ожидаемом виде;
- запрос инструмента проходит через протокол и возвращает результат;
- LM Studio корректно запускает сервер с выбранным Python и переменными окружения.

Для этого требуется отдельная проверка MCP-уровня. В следующем практическом прогоне открой настройки MCP в LM Studio, проверь запуск сервера и наличие двух инструментов. Затем выполни реальный поиск и загрузку страницы. Запиши отдельно:
1. версию LM Studio;
2. способ запуска сервера и путь к Python;
3. видны ли оба инструмента;
4. сработал ли поиск;
5. сработала ли загрузка страницы;
6. сообщения в логах при ошибке.

Не отмечай интеграцию как успешную, если проверены только автоматические тесты.

## 11. Частые ошибки при написании тестов

**Ошибка 1. Тест обращается к настоящему интернету.**  
Причина: HTTP-функция не была подменена. Решение: использовать `monkeypatch` и подготовленный ответ.

**Ошибка 2. Проверяется только `ok`.**  
Причина: тест не проверяет содержимое ответа. Решение: проверить ключевые поля, значения и отсутствие лишних сетевых вызовов в сценариях, где сеть не должна запускаться.

**Ошибка 3. Тест зависит от порядка запуска.**  
Причина: изменённое глобальное состояние не сбрасывается. Решение: использовать фикстуры pytest и локальные подмены; не сохранять изменяемое состояние между тестами.

**Ошибка 4. Тесты проходят, а LM Studio не видит инструмент.**  
Причина: проверены функции, но не MCP-протокол или конфигурация запуска. Решение: отдельно проверить интеграцию с клиентом.

**Ошибка 5. Считается, что высокий процент покрытия означает отсутствие ошибок.**  
Покрытие показывает, какие участки кода выполнялись, но не гарантирует, что тесты правильно проверили результат. Важны качество сценариев и значимые утверждения.

**Ошибка 6. Сеть замокирована слишком широко.**  
Если подменить слишком много функций, можно случайно скрыть ошибку в логике. Подменяй внешнюю границу — HTTP-вызов или проверку DNS — а парсинг HTML и построение результата оставляй настоящими.

## 14. Краткий словарь Python-конструкций урока

- `assert condition` — утверждение; проверяет условие.
- `lambda args: expression` — короткая анонимная функция.
- `*args` — сбор произвольных позиционных аргументов.
- `**kwargs` — сбор произвольных именованных аргументов.
- `monkeypatch.setattr(object, name, value)` — временная подмена атрибута в тесте.
- `def test_name():` — функция, которую pytest обнаруживает как тест.
- `is True` / `is False` — проверка логического значения по идентичности с `True` или `False`. Для простых сравнений часто допустимо `==`, но здесь явно проверяется логический результат.
- `None` — специальное значение Python, обозначающее отсутствие значения.

## 15. Критерии завершения урока

Урок считается освоенным, если ученик:
- понимает разницу между модульными, интеграционными и сквозными тестами;
- умеет запускать тесты через PowerShell;
- может объяснить, зачем сеть подменяется в автоматических тестах;
- проверяет и успешные ответы, и ошибки;
- понимает назначение лимитов, валидации URL и регрессионных тестов;
- не путает успешный запуск pytest с доказанной работоспособностью LM Studio;
- способен добавить новый тест по схеме «вход → ожидаемый результат → утверждения».
