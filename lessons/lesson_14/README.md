# Урок № 14. Типизация Python и контракты функций

## 1. Цель урока

На прошлом уроке мы вынесли настройки в переменные окружения и добавили логирование. Теперь разберёмся, как описывать входные и выходные данные функций так, чтобы код было проще читать, расширять и проверять.

Наш проект предоставляет LM Studio два MCP-инструмента:
- search_web — ищет страницы и возвращает заголовок, ссылку и краткое описание;
- fetch_web_page — загружает публичную HTML-страницу и возвращает извлечённый текст.

Обе функции возвращают словари. Но запись -> dict сообщает слишком мало: какие ключи есть в словаре? Какие типы у значений? Может ли ошибка быть представлена строкой или значением None? Чтобы ответить на эти вопросы, введём **контракты функций** — точное описание ожидаемых аргументов и результата.

В рамках урока мы изучим аннотации типов, разберём типы списков и необязательных значений, создадим contracts.py с описанием ответов, применим контракты в поиске, загрузчике и MCP-сервере, а затем проверим, что именно дают аннотации.

## 2. Иностранные термины

- **Type (тип)** — категория значения, например строка, целое число или логическое значение.
- **Type hint / type annotation (подсказка / аннотация типа)** — запись в коде, описывающая ожидаемый тип переменной, аргумента или результата функции.
- **Static type checker (статический анализатор типов)** — инструмент, который анализирует код и может находить несоответствия типов до запуска программы. Примеры: mypy и Pyright.
- **Runtime (время выполнения)** — момент, когда программа действительно выполняется.
- **Contract (контракт)** — соглашение о том, какие данные функция принимает и какие возвращает.
- **Return value (возвращаемое значение)** — результат, который функция передаёт через return.
- **Schema (схема)** — описание структуры данных: названий полей и типов.
- **TypedDict** — средство стандартной библиотеки Python для описания словарей с известными ключами и типами значений.
- **Union (объединение типов)** — описание значения, которое может иметь один из нескольких типов.
- **Optional (необязательный тип)** — распространённое название для значения, которое может быть указанного типа или None. В современном Python можно записать str | None.
- **Type safety (типовая безопасность)** — практика, уменьшающая вероятность ошибок из-за неправильных типов. Аннотации помогают, но сами по себе не обеспечивают полную типовую безопасность.
- **IDE (интегрированная среда разработки)** — программа для написания и анализа кода, например Visual Studio Code.
- **MCP tool (инструмент MCP)** — функция, которую MCP-сервер предоставляет клиенту, например LM Studio.

## 3. Аннотации типов: что они означают

~~~python
def make_greeting(name: str) -> str:
    return f"Привет, {name}!"
~~~

Разбор объявления:
- def начинает определение функции;
- make_greeting — имя функции;
- name: str означает, что аргумент name ожидается как строка;
- -> str означает, что функция должна возвращать строку;
- двоеточие начинает тело функции;
- return возвращает результат;
- f-строка подставляет значение name в фигурные скобки.

**Важное ограничение:** Python обычно не проверяет аннотации автоматически при каждом вызове. Передача числа вместо строки не обязательно немедленно вызовет ошибку. Аннотации помогают IDE, анализаторам и читателям кода. Если значение обязательно нужно проверить во время выполнения, пишите явную проверку или используйте библиотеку валидации.

### Аннотация и проверка — не одно и то же

~~~python
def repeat_text(text: str, count: int) -> str:
    if not isinstance(text, str):
        raise TypeError("text must be a string")
    if not isinstance(count, int) or isinstance(count, bool):
        raise TypeError("count must be an integer")
    if count < 0:
        raise ValueError("count must not be negative")
    return text * count
~~~

Аннотации : str, : int и -> str описывают интерфейс функции. isinstance() проверяет фактическое значение во время выполнения. Дополнительная проверка isinstance(count, bool) нужна потому, что в Python bool является подклассом int: без неё True будет принято как число 1. TypeError обычно указывает на неправильный тип, а ValueError — на неподходящее значение уже правильного типа.

Проверяйте данные особенно внимательно на границах доверия: при получении значений от пользователя, сайта, файла или внешней программы.

## 4. Почему одного dict недостаточно

Представим результат поиска:

~~~python
result = {
    "ok": True,
    "query": "Python MCP",
    "results": [
        {
            "title": "Документация",
            "url": "https://example.com",
            "snippet": "Описание страницы",
        }
    ],
    "error": None,
}
~~~

По значению видно, что внутри словаря четыре ключа. Но сигнатура -> dict не говорит, обязательно ли присутствует ok, является ли results списком строк или словарей, может ли error быть None и какие поля есть у каждого результата. Комментарии помогают, но могут устаревать. Контракт в виде типов делает структуру явной и помогает статическому анализатору обнаруживать часть ошибок.

## 5. Новый инструмент: TypedDict

В проект добавлен файл src/web_search_mcp/contracts.py:

~~~python
"""Структуры данных, возвращаемые инструментами MCP."""

from typing import TypedDict


class SearchResult(TypedDict):
    """Один результат веб-поиска."""

    title: str
    url: str
    snippet: str


class SearchResponse(TypedDict):
    """Единый контракт ответа инструмента поиска."""

    ok: bool
    query: str
    results: list[SearchResult]
    error: str | None


class FetchResponse(TypedDict):
    """Единый контракт ответа инструмента загрузки страницы."""

    ok: bool
    url: str
    status_code: int | None
    title: str
    text: str
    truncated: bool
    error: str | None
~~~

### Разбор по строкам

**from typing import TypedDict**

typing — стандартный модуль Python, в котором находятся средства описания типов. TypedDict предназначен для словарей с заранее известными ключами. В обычном словаре ключи могут быть разными, а значения — разными типами. В TypedDict мы документируем ожидаемые поля.

**class SearchResult(TypedDict):**

Мы объявляем описание структуры одного результата поиска. class создаёт новый класс или тип описания. Здесь TypedDict описывает словарь, который по-прежнему читается через result["title"], а не через result.title.

**title: str, url: str, snippet: str**

Это поля результата и ожидаемые типы их значений. Заголовок, URL и краткое описание представлены строками. Типы не гарантируют, что URL доступен или заголовок не пустой: такие ограничения требуют отдельных проверок.

**class SearchResponse(TypedDict):**

Это контракт полного ответа поиска:
- ok: bool — операция успешна или нет;
- query: str — запрос;
- results: list[SearchResult] — список элементов описанной структуры;
- error: str | None — текст ошибки или отсутствие ошибки.

**list[SearchResult] — составной тип.** Внешний тип — список, а тип каждого элемента — SearchResult. Мы описываем не просто список, а список словарей с полями title, url и snippet. Такая запись поддерживается Python 3.9 и новее.

**str | None — объединение типов.** Вертикальная черта | означает «или»: поле содержит строку либо значение None. Этот синтаксис поддерживается Python 3.10 и новее. В более старом коде можно встретить Optional[str] или Union[str, None].

В FetchResponse поле status_code: int | None может содержать HTTP-код, например 200, или None, если HTTP-ответ не был получен. Поле truncated: bool сообщает, был ли текст обрезан. Поле text: str остаётся строкой и при ошибке: тогда используется пустая строка.

### Преимущества TypedDict

1. Структура ответа описана в одном месте.
2. IDE может подсказывать имена полей.
3. Анализатор типов может находить пропущенные поля и значения неподходящего типа.
4. По сигнатуре проще понять интерфейс функции.
5. Изменения контракта можно проверять централизованно.

### Чего TypedDict не делает

TypedDict сам по себе не валидирует словарь во время выполнения и не преобразует его в специальный объект. Если сайт вернул неожиданные данные, аннотация не исправит их автоматически. Кроме того, поле ok: bool не заставляет Python связывать ok=True с error=None. В проекте мы соблюдаем это соглашение во всех ветвях кода; более строгий вариант можно построить через отдельные типы успеха и ошибки.

## 6. Применяем контракт к поиску

В src/web_search_mcp/web_search.py добавлен импорт:

~~~python
from .contracts import SearchResponse, SearchResult
~~~

Сигнатура функции теперь такая:

~~~python
def web_search(
    query: str,
    max_results: int = DEFAULT_MAX_SEARCH_RESULTS,
) -> SearchResponse:
~~~

query: str — ожидаемая строка запроса. max_results: int — ожидаемое целое число. Значение после = — аргумент по умолчанию: если вызывающий код не передал лимит, используется конфигурационная настройка. -> SearchResponse описывает структуру результата.

Раньше список создавался так:

~~~python
results = []
~~~

Теперь он объявлен так:

~~~python
results: list[SearchResult] = []
~~~

Новая часть : list[SearchResult] поясняет, что в список должны добавляться результаты соответствующей структуры. Сам список создаётся тем же оператором присваивания = и квадратными скобками []. Аннотация не меняет способ хранения данных.

Добавление результата остаётся привычным:

~~~python
results.append({
    "title": title,
    "url": urljoin(SEARCH_URL, href),
    "snippet": description,
})
~~~

append() добавляет элемент в конец списка. Статический анализатор может проверить, что словарь соответствует SearchResult, но возможности проверки зависят от анализатора и его настроек.

Ветка ошибки тоже возвращает словарь с ключами ok, query, results и error. Это позволяет вызывающему коду обрабатывать ответ единообразно.

## 7. Применяем контракт к Web Fetch

В src/web_search_mcp/web_fetch.py импортирован тип:

~~~python
from .contracts import FetchResponse
~~~

Вспомогательная функция ошибки имеет сигнатуру:

~~~python
def _error_result(
    url: str,
    error: str,
    status_code: int | None = None,
) -> FetchResponse:
    return {
        "ok": False,
        "url": url,
        "status_code": status_code,
        "title": "",
        "text": "",
        "truncated": False,
        "error": error,
    }
~~~

_error_result — внутренний помощник. Начальное подчёркивание в имени является соглашением: функция предназначена для внутреннего использования модулем. Параметр status_code можно не передавать, потому что у него есть значение по умолчанию None. Аннотация int | None отдельно описывает возможный тип значения.

Различайте два понятия:
- **необязательный аргумент** — его можно не передавать, потому что у него есть значение по умолчанию;
- **необязательное значение** — значение может быть None, что указывается типом int | None.

Аргумент может быть обязательным, но допускать None: def f(value: int | None). И наоборот, аргумент может иметь значение по умолчанию, но тип допускает только строки: def f(name: str = "Гость").

Основная функция также объявлена с результатом FetchResponse:

~~~python
def web_fetch(
    url: str,
    max_chars: int = DEFAULT_MAX_PAGE_CHARS,
    timeout: float = DEFAULT_TIMEOUT_SECONDS,
) -> FetchResponse:
~~~

float обозначает число с плавающей точкой. Тайм-аут может быть дробным, например 2.5 секунды. Внутри функции фактические типы аргументов дополнительно проверяются через isinstance() и условия диапазона.

## 8. Контракты на уровне MCP-сервера

В src/web_search_mcp/server.py добавлен импорт:

~~~python
from .contracts import FetchResponse, SearchResponse
~~~

Обёртки MCP теперь явно указывают возвращаемые типы:

~~~python
@mcp.tool()
def search_web(
    query: str,
    max_results: int = DEFAULT_MAX_SEARCH_RESULTS,
) -> SearchResponse:
    """Search the web and return page titles, URLs, and snippets."""
    return web_search(query=query, max_results=max_results)


@mcp.tool()
def fetch_web_page(
    url: str,
    max_chars: int = DEFAULT_MAX_PAGE_CHARS,
) -> FetchResponse:
    """Fetch a web page and return its title and readable text."""
    return web_fetch(url=url, max_chars=max_chars)
~~~

Декоратор @mcp.tool() регистрирует функцию как доступный инструмент MCP. Декоратор — конструкция Python, позволяющая обернуть или зарегистрировать функцию без отдельного явного вызова регистрации. Аннотации аргументов и документация важны не только разработчикам: MCP-библиотека использует описание инструмента для формирования входной схемы. Возвращаемый TypedDict прежде всего служит контрактом в коде и для статического анализа; он не гарантирует автоматическую проверку каждого ответа во время выполнения.

Обёртка сервера намеренно остаётся простой: логика поиска находится в web_search, загрузка и обработка страницы — в web_fetch. Сервер предоставляет эти функции клиенту MCP.

## 9. Как читать типы в сигнатуре

| Запись | Значение |
|---|---|
| name: str | аргумент ожидается как строка |
| count: int | аргумент ожидается как целое число |
| timeout: float | аргумент ожидается как число с плавающей точкой |
| -> bool | функция возвращает логическое значение |
| list[str] | список строк |
| dict[str, str] | словарь со строковыми ключами и значениями |
| str | None | строка или None |
| int | None = None | аргумент может содержать целое число или None, а при пропуске получает None |
| list[SearchResult] | список словарей структуры SearchResult |
| -> SearchResponse | функция возвращает словарь структуры SearchResponse |

Запись dict[str, str] не подходит для ответа поиска: значения имеют разные типы — bool, str, список и None. Поэтому слишком общий или неправильный тип может скрыть реальные особенности данных. TypedDict точнее описывает набор полей.

## 11. Частые ошибки и заблуждения

- **«Если я написал query: str, Python обязательно запретит число».** Нет. Аннотация сама по себе не является проверкой времени выполнения.
- **«TypedDict создаёт специальный словарь».** Нет. Во время выполнения это обычный словарь; TypedDict описывает структуру для анализа типов.
- **«str | None означает, что аргумент можно не указывать».** Нет. Это значит, что значение может быть строкой или None. Чтобы аргумент можно было пропустить, нужно значение по умолчанию.
- **«dict — достаточно точный тип для любого ответа».** Нет. Он не сообщает ключи и типы значений.
- **«ok: bool гарантирует, что при ok=False поле error обязательно заполнено».** Нет. Обычный TypedDict не устанавливает эту зависимость автоматически.
- **«Если импорты работают, значит инструмент работает».** Нет. Импорт не проверяет сеть, HTML-разметку сайта и вызов инструмента в LM Studio.
- **«Аннотации заменяют тесты».** Нет. Аннотации описывают интерфейс и помогают находить часть ошибок, а тесты проверяют поведение.

## 15. Итог урока

В этом уроке мы заменили расплывчатые аннотации dict на описания конкретных структур ответов. Создали SearchResult, SearchResponse и FetchResponse с помощью TypedDict, указали типы списков и необязательных значений, а затем применили контракты к функциям поиска, загрузки страницы и обёрткам MCP-сервера.

Главное:
- аннотации делают интерфейс понятнее, но сами по себе не проверяют данные при выполнении;
- TypedDict документирует структуру словаря и помогает статическому анализу;
- str | None описывает два допустимых варианта значения;
- одинаковый контракт упрощает обработку результата клиентским кодом;
- успешный импорт не равен успешному сетевому или интеграционному тесту.

**Критерии готовности:** можешь объяснить аннотации, описать структуру словаря через TypedDict, отличить аннотацию от проверки времени выполнения, найти все ветви возврата и объяснить, почему они должны соответствовать контракту.
